# agentdeck v1 spec

The decisions behind this spec, and their reasons, are in [the v1 map](https://github.com/bRRRITSCOLD/agentdeck/issues/1). This file is the build contract: what to build, not why. When code and spec disagree, change one of them in the same PR.

## 1. Programs and crates

One Cargo virtual workspace, pinned like rust-packages: GPUI pin, toolchain 1.99.1, edition 2024, resolver 3, inherited lints. Crates live under `crates/`.

| Crate | Kind | Depends on | Notes |
|---|---|---|---|
| `agentdeck-core` | lib | — | Domain types, ids, state rules engine, no IO, no GPUI, no tokio |
| `agentdeckd` | bin | core | tokio, dropshot, rusqlite, portable-pty, alacritty_terminal, keyring-core with the keyring project's Secret Service store (§8) |
| `agentdeck-client` | lib | core | progenitor output from `openapi.json`, checked in, built by `cargo xtask client`; plus `daemon` (find, start or restart the daemon, §2) and `ws` (the `/v1/ws` client, §5), shared by the CLI and the GUI |
| `agentdeck` | bin | core, client | CLI and `agentdeck mcp` (rmcp); no GPUI. A current-thread tokio runtime drives the async client and the MCP server |
| `agentdeck-gui` | bin | core, client, notify, `brrritscold-core-gpui` | GPUI app. A small multi-thread tokio runtime, kept as a GPUI global, drives the client and the socket |
| `agentdeck-notify` | lib | — | The GUI's desktop notifications: the freedesktop notifications D-Bus API over one zbus connection, on zbus's own runtime (no tokio); clicks reach GPUI's foreground (§11) |
| `xtask` | bin | — | `openapi` (regenerate spec), `client` (regenerate client), `ci` |

## 2. Daemon

- **Start:** the GUI or the CLI runs `agentdeckd` detached when it can't reach the daemon in `daemon.json`. The daemon a client starts is its child, so the client reaps it whenever it exits (it stops, crashes or is killed), and a long-lived client such as the GUI never keeps it as a zombie. A zombie pid in `daemon.json` counts as not running, and so does one that doesn't answer `/v1/health` within 1 s, as the daemon's own check below: a daemon stopped with SIGSTOP, held in a debugger or deadlocked still accepts connections but never answers, so the client starts a new daemon instead of waiting on it, and reports that daemon's failure (below) instead of hanging. An optional systemd user unit is `contrib/agentdeckd.service`. Only one daemon runs per user: it holds a lock on `$XDG_RUNTIME_DIR/agentdeck/lock` until it exits.
  - **Lock taken:** while another daemon holds the lock and the daemon in `daemon.json` answers `/v1/health` (with its token, within 1 s), that one serves, so a new daemon exits 1 at once (`another agentdeckd is running`); a client that started it keeps looking at `daemon.json` for 2 s, in case it lost the race to another client's daemon. While the lock is held with no `daemon.json`, or with one that answers nothing, its holder is shutting down, won the race and doesn't serve yet, or was killed or crashed and is still exiting (it leaves `daemon.json` behind, and holds the lock until the kernel has closed its files). So the new daemon waits up to 10 s for the lock, polling it, then writes its own `daemon.json`. It gives up at once when the daemon in `daemon.json` answers, and exits 1 after 10 s (`the agentdeckd that holds … hasn't exited after 10s`). A client gives the daemon it started 20 s to serve, to cover that wait.
  - **Stop:** on SIGINT or SIGTERM the daemon removes `daemon.json` first, then closes its terminals and its HTTP server and gives queries in flight 500 ms, and releases the lock only as it exits. A client that connects meanwhile (`pkill -TERM agentdeckd`, then the GUI or the CLI) starts a new daemon, which waits for the lock and then resumes the panes; the lock keeps them from being resumed twice.
- **Endpoint:** `127.0.0.1:<random>`. On start it writes `$XDG_RUNTIME_DIR/agentdeck/daemon.json` (mode 0600): `{ "port", "token", "pid", "version", "api_version" }`. Every request, including the WebSocket upgrade, carries `Authorization: Bearer <token>`.
- **API version:** `api_version` is `agentdeck_core::API_VERSION`, an integer. **It is bumped in the same PR whenever a route, a field or a message is added or changed**: an endpoint or its request or response in `openapi.json`, a WebSocket message (§5), a `daemon.json` field. A daemon unit test pins `openapi.json`'s fingerprint to the version, so changing the file without a bump fails; the WebSocket and `daemon.json` types say so in their doc comments.
  - The GUI and the CLI compare it with their own as they connect. A lower one, or none (a daemon from before the field, read as `0`), is a daemon **older than the client**, which may lack what the client asks of it: the GUI shows a banner with **Restart** (§11) and the CLI warns (§10). A newer daemon still serves an older client. Neither ever restarts the daemon on its own, since every running agent is re-spawned: the user chooses when.
  - **Restart** (`agentdeck_client::daemon::restart`) is `kill -TERM <pid>` for the daemon the client reached, and only while `daemon.json` still names it by pid and token (a pid alone may have been reused; once another daemon replaced it, the client just connects to that one). It waits up to 10 s for that process to exit, so its lock is free; then it reaches a new daemon the usual way, starting it. The new daemon resumes the panes (§6).
- **Data:** `$XDG_DATA_HOME/agentdeck/agentdeck.db` (SQLite, WAL). Scratch workspaces live in `$XDG_DATA_HOME/agentdeck/workspaces/<slug>/`. Config is `$XDG_CONFIG_HOME/agentdeck/config.toml`, which the daemon owns: it reads the file at start, and clients read and change the settings only through `GET` / `PATCH /v1/settings` (§4), so the GUI, the CLI and PR sync share one copy. The file need not exist. The GitHub token and the OAuth client ID are not settings and are never in it: both live in the system keyring (§8).
  - **Settings:** `[appearance] theme` (`system` | `dark` | `light`, default `system`; the GUI's theme, §11), `[pr_sync] max_age_days` (a count of days, default `90`, `0` for no cutoff; §8) `[terminal] file_opener` (a command, default `xdg-open {path}`; what a `secondary`-click on a file path in a pane runs, §11) and `[gui] confirm_quit` (`true` | `false`, default `true`; whether the GUI asks before quitting while agents run, §11). Each is named by its dotted key, `appearance.theme`.
    - `file_opener` is split into words as a shell would split it (`shell-words`) and never run through a shell. One argument after the program must hold `{path}`, the file's absolute path; `{line}` and `{col}` are the line and column the path names, `1` when it names none. A value that is blank, doesn't split (an unclosed quote) or passes no `{path}` is refused (`invalid_setting`), and in the file gives the default.
  - **Reading:** a missing file or key gives the default; a value of the wrong kind gives that key's default; a key the daemon doesn't know is ignored; a file that doesn't parse is logged and every default applies, as a state rule file's is (§7).
  - **Writing:** a PATCH re-reads the file, changes only its keys with `toml_edit`, so every other key, table and comment stays, and writes a temp file beside it that it renames over it, creating the dir if need be. A file that doesn't parse is left as it is: the PATCH is `409 unparsable_config`. A change applies at once, with no restart.
  - **Environment overrides:** `AGENTDECK_PR_MAX_AGE_DAYS` overrides `pr_sync.max_age_days` (§8). The settings then report the variable's value and list the key in `overridden_by_env`. A PATCH of an overridden key still writes the file and answers 200, but the variable's value stays in use, and the key stays in `overridden_by_env`, until the daemon runs without it.
    - The GitHub variables aren't settings and never show in `overridden_by_env`: `GH_TOKEN` / `GITHUB_TOKEN` give the token and `AGENTDECK_GITHUB_CLIENT_ID` the OAuth client ID, each only while none is saved in the keyring (§8).
- **DB access:** rusqlite on one owned connection behind a `spawn_blocking` actor. Migrations are embedded SQL run by `rusqlite_migration` at start.
- **Logging:** `tracing`, to `$XDG_STATE_HOME/agentdeck/agentdeckd.log` and stderr. The GUI logs to its own file beside it (§11).

## 3. Data model

Ids are UUIDv7 strings. Times are RFC 3339 UTC strings; the daemon stamps them to the microsecond (`2026-11-14T10:00:00.123456Z`), so they sort as text and an edit right after a create still stamps later. Rows written before that carry milliseconds, which still sort before every later stamp.

```sql
CREATE TABLE workspaces (
  id TEXT PRIMARY KEY, slug TEXT NOT NULL UNIQUE, name TEXT NOT NULL,
  dir TEXT NOT NULL,                 -- absolute path
  dir_owned INTEGER NOT NULL,        -- 1 = scratch dir agentdeck created, 0 = attached
  muted INTEGER NOT NULL DEFAULT 0,  -- notifications
  archived_at TEXT, created_at TEXT NOT NULL
);
CREATE TABLE tabs (
  id TEXT PRIMARY KEY, workspace_id TEXT NOT NULL REFERENCES workspaces ON DELETE CASCADE,
  title TEXT NOT NULL, position INTEGER NOT NULL,
  layout TEXT NOT NULL               -- JSON split tree: {"pane":id} | {"split":"h"|"v","ratio":f,"a":…,"b":…}; JSON null until the tab has a pane
);
CREATE TABLE panes (
  id TEXT PRIMARY KEY, tab_id TEXT NOT NULL REFERENCES tabs ON DELETE CASCADE,
  kind TEXT NOT NULL,                -- 'agent' | 'shell'
  agent TEXT,                        -- 'claude' | 'codex' | 'other' (agent panes)
  hosted_agent TEXT,                 -- 'claude' | 'codex' while a shell pane hosts that agent (§7); NULL otherwise
  argv TEXT NOT NULL,                -- JSON array, as launched (without resume flags)
  cwd TEXT NOT NULL,
  session_id TEXT,                   -- chosen by agentdeck at launch (claude) or discovered (codex)
  task_id TEXT REFERENCES tasks ON DELETE SET NULL,
  state TEXT NOT NULL DEFAULT 'unknown', -- working|blocked|done|idle|unknown|exited
  title TEXT NOT NULL DEFAULT '', exit_code INTEGER, created_at TEXT NOT NULL
);
CREATE TABLE tasks (
  id TEXT PRIMARY KEY, title TEXT NOT NULL, body TEXT NOT NULL DEFAULT '',
  status TEXT NOT NULL DEFAULT 'todo', -- todo|doing|review|done
  kind TEXT NOT NULL DEFAULT 'plain',  -- plain|pr
  workspace_id TEXT REFERENCES workspaces ON DELETE SET NULL,
  created_at TEXT NOT NULL, updated_at TEXT NOT NULL, done_at TEXT
);
CREATE TABLE pull_requests (
  task_id TEXT PRIMARY KEY REFERENCES tasks ON DELETE CASCADE,
  repo TEXT NOT NULL, number INTEGER NOT NULL, url TEXT NOT NULL,
  state TEXT NOT NULL,               -- open|merged|closed
  draft INTEGER NOT NULL, head_ref TEXT NOT NULL,
  checks TEXT,                       -- pending|success|failure|NULL
  review TEXT,                       -- approved|changes_requested|review_required|NULL
  updated_at TEXT NOT NULL, synced_at TEXT NOT NULL,
  aged_out_at TEXT,                  -- when PR sync aged it out (§8); NULL otherwise
  workspace_picked_at TEXT,          -- when the user last set the task's workspace (§8); NULL while sync's match decides
  UNIQUE (repo, number)
);
CREATE TABLE comments (
  id TEXT PRIMARY KEY,
  task_id TEXT NOT NULL REFERENCES tasks ON DELETE CASCADE,
  body TEXT NOT NULL,
  author TEXT NOT NULL,              -- user|agent
  author_agent TEXT,                 -- claude|codex|NULL
  author_pane TEXT REFERENCES panes ON DELETE SET NULL,
  created_at TEXT NOT NULL,
  delivered_at TEXT, delivered_to_pane TEXT,
  seen_at TEXT                       -- when the user saw an agent's comment; NULL = new
);
CREATE TABLE instructions (
  id TEXT PRIMARY KEY,
  workspace_id TEXT NOT NULL REFERENCES workspaces ON DELETE CASCADE,
  body TEXT NOT NULL,
  created_at TEXT NOT NULL, updated_at TEXT NOT NULL
);
```

A pane links to at most one task (`panes.task_id`). A task shows its linked agent panes by querying in the other direction.

A shell pane **hosts** an agent while one the user started in it by hand (`claude`, `codex`) is its foreground process (§7). `kind` stays `shell`; `hosted_agent` names the agent while it runs and is NULL again once it leaves the foreground, when the daemon starts, and when the pane exits. An agent pane never hosts one. Wherever this spec speaks of a pane's agent, a hosting shell pane's is its `hosted_agent`, and "an agent pane" includes it while it hosts one, unless it says otherwise.

An agent pane runs its agent only until its process exits. An exited agent pane keeps `kind` and `agent`, so it can be restarted (`POST /v1/panes/{id}/respawn`, §4), but it is no longer one of its task's agent panes: nothing is typed into it and nothing is held for it (§9). An agent pane that comes back as a shell (§6), or that the user turns into one, **becomes a shell pane**: `kind` `shell`, `agent` and `session_id` NULL, `argv` the shell. It keeps its `cwd` and its task link.

Migration `0002` replaced v1's first `notes` table (a note on exactly one of a workspace and a task, with `read_at` and `read_by_pane`): task notes became the user's comments (`read_at` → `delivered_at`, `read_by_pane` → `delivered_to_pane`, seen), workspace notes became instructions, and `notes` was dropped. Migration `0003` added `pull_requests.aged_out_at`, `0004` `pull_requests.workspace_picked_at`, and `0005` `panes.hosted_agent`.

v1.1 adds `channels`, `channel_members` and `messages` in their own migration.

## 4. HTTP API (`/v1`, dropshot)

`openapi.json` is generated by `cargo xtask openapi` and committed. A unit test fails when it differs from what the code generates. Errors use dropshot's `HttpError`, and an expected domain failure is its own status with a `code` field (`error_code`): `unauthorized` 401, `not_found` 404, `dirty` 409, `exited` 409 (input to a pane whose process has exited), `unparsable_config` 409 (a settings PATCH while `config.toml` doesn't parse), `no_client_id` 409 (a sign-in with no OAuth client ID, §8), `invalid_token` 422 (a token GitHub doesn't accept, or a blank one), `github_error` 502 (GitHub refused a sign-in or couldn't check a token; the message is GitHub's), `no_keyring` 503 (no Secret Service to save a token or client ID in), and 400 for `invalid_setting` (a key that isn't a setting, or a value it can't take; the message starts with the dotted key), `invalid_name`, `invalid_dir`, `invalid_title`, `invalid_layout`, `invalid_target`, `invalid_argv`, `invalid_task` (a task in another workspace than the pane's, or done), `invalid_client_id` (a blank OAuth client ID, or one shaped like a sign-in code), `unsupported_kind`, `unknown_workspace`, `unknown_tab`, `unknown_task`, `unknown_pane`. `DELETE /v1/workspaces/{id}`'s error body adds `dirty`, the dirty report. A route or method the daemon doesn't have is dropshot's own 404 or 405 with no `error_code`; every domain failure has one, so the client reads a code-less 404 or 405 as a daemon older than itself (§2) and says "agentdeck's background service is older than this app and can't do this yet. Restart it to use new features; your agents resume after the restart.", never a bare "Not Found". Every route takes a request body of up to 1 MiB (1,048,576 bytes), set once for the server (dropshot's default is 1 KiB); a larger body is dropshot's own 400 with no `error_code` and the message "request body exceeded maximum size of 1048576 bytes", and changes nothing. Every endpoint below is in v1.

Every pane in a response (`POST`, `GET` and `PATCH` on `/v1/panes`) carries `hosted_agent`: `claude` or `codex` while a shell pane hosts that agent (§3, §7), else null. It came with `API_VERSION` 6.

| `DELETE /v1/workspaces/{id}?force=` | without `force`: `409 dirty` with the dirty report. Removes the dir only if `dir_owned` |

The client places the pane in the tab's `layout` |

The pane's state starts over (`unknown`, no exit code). 409 `running` while its process hasn't exited; `invalid_dir` when its `cwd` is gone; a program that can't start is `invalid_argv`, and the pane stays exited. ## 5. WebSocket (`/v1/ws`)

One connection per client.
- **Binary frames** carry terminal bytes: `[u32 channel, big-endian][bytes]`. Client → daemon is PTY input; daemon → client is a snapshot or live output.
- **Text frames** are JSON tagged with `t`.

Client → daemon:
```json
{"t":"attach","pane":"<id>","channel":3}
{"t":"detach","channel":3}
{"t":"resize","channel":3,"cols":120,"rows":40}
{"t":"primary","channel":3}
```
Daemon → client:
```json
{"t":"attached","channel":3,"pane":"<id>","cols":100,"rows":30,"title":"✳ Claude Code","state":"idle"}
{"t":"resize","channel":3,"cols":120,"rows":40}
{"t":"title","channel":3,"title":"◐ Claude Code"}
{"t":"state","pane":"<id>","state":"working"}
{"t":"exit","pane":"<id>","code":0}
{"t":"changed","entity":"task","id":"<id>"}
{"t":"github_auth","device":"signed_in"}
{"t":"lagged","channel":3}
{"t":"resync"}
{"t":"error","channel":3,"code":"not_found","message":"…"}
```
The message types are `agentdeck_core::ws::{ClientMessage, ServerMessage}`.
- **Attach:** the daemon sends `attached`, then one binary frame holding the **snapshot**, then live bytes. The snapshot and the live subscription are taken under one lock, so no output is lost or doubled.
  - The snapshot is the daemon's `Term` re-encoded as escape sequences (SGR runs, cursor, modes). It includes scrollback and the primary screen under an alternate screen.
  - The client feeds it into a fresh `alacritty_terminal::Term` of the `attached` size. It starts with a full reset, so a reused `Term` works too.
  - It does not carry the scroll region, tab stops or the active character set, which `alacritty_terminal` keeps private.
  - It ends with the shell's last OSC 7 (`ESC ] 7 ; <uri> ST`), which a `Term` ignores, so a client reading OSC 7 for file paths (§11) has the directory from the attach on. Nothing else changes: an older client's `Term` drops it.
  - Attaching a channel that is already attached replaces it.
- **Resize:** the **primary** client's size wins. The most recent client to send `primary` (the focused GUI window) is primary; until one does, or after it detaches, any client's resize applies. A resize from any other client is ignored and answered with `resize` carrying the size the pane keeps. Sending `primary` applies the size that client last asked for. Other attached clients get `resize` when the size changes; bytes after it were written at the new size.
- **Terminal queries** (DA, cursor position, …) are answered only by the daemon's `Term`. Clients drop the replies their own `Term` generates.
- **Backpressure:** a client more than 1 MiB behind on a channel gets `lagged`. It then re-attaches for a fresh snapshot.
- **Data events:** `changed` tells clients to refetch an entity over REST: `workspace`, `tab`, `pane`, `task`, `comment` or `instruction`, after it is created, changed or deleted (a pane also when an agent starts or stops being hosted in it, §7; a comment also when it is delivered or seen; its task too when an agent writes one or it is seen, since the task's `unseen_agent_comments` changed); `pr_sync` (id `status`) means `GET /v1/prs/status`, when a PR sync begins, reads a page or ends, or a PATCH changes the age cutoff; `settings` (id `settings`) means `GET /v1/settings`, after every PATCH. `state` and `exit` are sent to every client, attached or not. The daemon subscribes a connection to these events before it answers the upgrade, so every event published after the client sees the 101 reaches it.
- **Resync:** a connection that falls more than 1024 events behind misses some. It gets `resync` in their place (and the daemon logs it at info), then the events after. A client reads everything it shows again over REST, as on a `changed` for each entity, and compares what it reads with what it had, so a change made meanwhile still notifies (§11).
- **GitHub auth:** `github_auth` means `GET /v1/github/auth` (§8), sent to every client after a token or client ID is saved or deleted, after a re-read changes the token's source, login or `rejected`, when PR sync finds GitHub rejecting a token it accepted a moment ago, and when a sign-in ends. Only then does it carry `device`: `signed_in`, `expired`, `denied`, or `failed` with GitHub's `message`. It never carries the token, the client ID or the user code.
- **Errors:** a message the daemon can't act on gets `error` with a `code`: `not_found` (attach to a pane that isn't live), `not_attached` (a channel with nothing attached), `invalid_message`.

## 6. Launching agents

- **Environment:** built from an allowlist: `PATH HOME USER SHELL LANG LC_* TERM COLORTERM XDG_* SSH_AUTH_SOCK GH_* EDITOR CODEX_HOME`, plus `TERM=xterm-256color` and `COLORTERM=truecolor`. Nothing else from the daemon's own environment is passed on, and that rule is tested. On top: `AGENTDECK_PANE` and `AGENTDECK_WORKSPACE` in every pane, and `AGENTDECK_TASK` in a pane linked to a task when it is spawned (launched or resumed); linking later doesn't change it, so the CLI and MCP read the pane's current link instead (§10).
- **MCP server:** `claude` and `codex` panes, new and resumed, get agentdeck's MCP server (§10) as `agentdeck`, on top of the user's own servers: the `agentdeck` beside `agentdeckd`'s executable, else `agentdeck` from `PATH` (logged at warn), run as `<agentdeck> mcp`. These `<mcp flags>` come right after the program.
  - `claude`: `--mcp-config '{"mcpServers":{"agentdeck":{"command":"<agentdeck>","args":["mcp"]}}}'`. It takes every value up to the next flag, so a flag follows it, never the prompt. No `--strict-mcp-config`.
  - `codex`: `-c mcp_servers.agentdeck.command="<agentdeck>" -c 'mcp_servers.agentdeck.args=["mcp"]' -c 'mcp_servers.agentdeck.env_vars=[…]'`. Codex passes an MCP server only `HOME`, `PATH` and a few more of its own, so `env_vars` names what `agentdeck mcp` reads: `XDG_RUNTIME_DIR XDG_CONFIG_HOME XDG_DATA_HOME XDG_STATE_HOME AGENTDECK_PANE AGENTDECK_WORKSPACE AGENTDECK_TASK`. Claude Code passes its whole environment.
- **Argv by agent:** `claude` and `codex` are looked up on the pane's `PATH`, so tests put stubs first.
- **A program that can't start** is refused with 400 `invalid_argv` and the pane row is dropped. When `argv[0]` is a bare name in none of the pane's `PATH` directories, the message is only what to do: "`codex` isn't on agentdeckd's PATH. Install it, or start agentdeckd from a shell where it's found."; the lookup's whole error, which lists every `PATH` directory, goes to `agentdeckd.log` at warn. Any other spawn error keeps its text. The GUI's toast and `agentdeck agent new` show an `invalid_argv` refusal as that message alone.
  - `claude`: `claude <mcp flags> --session-id <uuid> [<launch prompt>]`, with a UUIDv4 agentdeck chooses.
  - `codex`: `codex <mcp flags> [<launch prompt>]`. Codex has no flag to start on a chosen session id (checked against `openai/codex` on 2026-11-11: `codex resume <id>` and `codex fork <id>` only). It writes each session to `$CODEX_HOME/sessions/YYYY/MM/DD/rollout-<timestamp>-<uuid>.jsonl` (`CODEX_HOME` from the pane's environment, default `$HOME/.codex`). The daemon lists those files just before launch, then polls every 250 ms for up to 2 min, while the pane runs, for the newest new one whose id no other pane holds, and stores its id as `session_id` (a `changed` pane event follows).
  - `other` and `shell`: argv as given.
  - `panes.argv` holds the argv as first launched, launch prompt included.
- **Launch prompt** for `claude` and `codex` panes: the linked task's title, id, how to report back on it and body, then every instruction for the pane's workspace, oldest first, then the task's user comments no agent has had yet, oldest first. Those comments are then marked delivered to this pane. Either block is left out when empty; with no task and no instructions, there is no prompt argument. `other` panes get no prompt.

  ```
  Task: <title>
  Task id: <id>
  Report back with the agentdeck MCP tools: task_comment to comment on this task, task_update to set its status (or run `agentdeck comment add --task <id> <text>`).

  <body>

  Instructions for this workspace:
    - <instruction>
    - <instruction, continuation lines indented four spaces>
  Comments since your last session:
    - <comment>
  ```
- **Trust dialog:** never answered automatically. The launch prompt goes in as an argument, and input agentdeck types on its own (a task on linking and comment delivery, §9) waits until the pane is `idle` or `done`, never `blocked`, so it can't answer any dialog. The GUI focuses the new pane so you can answer it.
- **Resume after a restart:** at start, before it serves, the daemon re-spawns each pane whose state isn't `exited`. Exits aren't recorded while the daemon shuts down, so those are the panes that were alive. Their rows, and so the layout, are unchanged.
  - `claude` panes as `claude <mcp flags> --resume <session_id>`.
  - `codex` panes as `codex <mcp flags> resume <session_id>`; one whose session was never found comes back as a shell.
  - All other panes as `$SHELL` (else `/bin/sh`) in their `cwd`, with the `shell` rules and hosting on (§7), so an agent the user starts there is hosted. An agent pane that comes back this way (a `codex` pane whose session was never found, an `other` agent's) becomes a shell pane (§3), saved before it starts, so it no longer counts as its task's agent and its menu no longer offers Link to task. A shell pane that hosted an agent comes back as that shell alone: the hosted agent isn't resumed, and `hosted_agent` is NULL until the user starts one again.
  - A pane that can't be re-spawned (its `cwd` is gone, say) is marked exited.
  - A pane that had exited stays exited.

## 7. Agent state

`agentdeck-core::state` evaluates **rules**: data files, embedded defaults that a file in `$XDG_CONFIG_HOME/agentdeck/rules/<agent>.toml` can override. A file that doesn't parse is logged and the defaults apply. Shell panes read `rules/shell.toml`; none is shipped, so a shell is `working` while it prints and `unknown` otherwise. Inputs are the foreground process name, the OSC 0/2 title, the last N screen rows, OSC 9;4 and OSC 7501, and time since the last output.

```toml
agent = "claude"
process = ["claude"]

[[rule]]                       # first match wins
state = "blocked"
rows = "bottom:1"
contains = ["Esc to cancel"]

[[rule]]
state = "working"
title_regex = '^[◐◓◑◒]'

[[rule]]
state = "idle"
title_regex = '^✳'

[settle]
min_ms = 400                   # a new state must hold this long before it is published
```

- **Rule keys:** a rule names a `state` (`working`, `blocked` or `idle`) and one or more conditions, all of which must hold:
  - `title_regex`, matched against the title;
  - `contains`, strings that must each appear in `rows`, which is `screen` (the default) or `bottom:N`, the last N non-blank rows of the live screen;
  - `progress`, OSC 9;4 states (`removed`, `normal`, `error`, `indeterminate`, `paused`);
  - `program_status`, OSC 7501 states (`idle`, `working`, `done`, `blocked`, `error`).
  The rules apply only while a `process` entry is in the foreground, or when the foreground process can't be read. `done`, `unknown` and `exited` come from the evaluator, never from a rule.
- **done vs idle:** `done` is published when a pane goes working → idle. It turns back to `idle` once the pane is focused, or after a new prompt.
- **Exit:** a dead process is `exited`, whatever the rules say. The daemon waits on each pane's process rather than on its PTY, since a child it leaves running (a background job, an MCP server) keeps the PTY open. Once the process has exited, the pane is exited as soon as its PTY closes, or 1 s later if something still holds it; then every process left in the pane's session gets SIGHUP, so the PTY closes. A child that started a session of its own is out of reach and may keep the old PTY until the pane is closed or respawned. The daemon saves the exit to the pane's row before anything reports it: the `state` `exited` and `exit` events and `GET /v1/panes/{id}` show it only once the row says `exited`, so archiving the workspace right after is never refused for that pane (`panes_running`).
- **No match:** the state is `unknown`, unless the pane has produced output in the last 2 s, in which case it is `working`. Output within 300 ms of a resize is a redraw and doesn't count, nor does a shell pane's before anything is typed into it (its prompt), so a new or resized shell stays `unknown`.
- **Hosted agents:** a shell pane runs the `shell` rules until its foreground process is `claude` or `codex`, as that agent's `process` list (its rule file's, so an override applies) names it. From then on the pane **hosts** that agent (`hosted_agent`, §3): it runs that agent's rules, and goes back to the `shell` rules once the agent leaves the foreground (it exits, or the user suspends it).
  - A listed name other than the agent's own, such as `node` for an npm install of Claude Code, counts only while the process runs the agent's script: its first argument that isn't a flag is a file named after the agent (`…/bin/claude`, `codex.js`), or sits in its npm package (`@anthropic-ai/claude-code`, `@openai/codex`). So `node server.js` in a shell is still a shell.
  - The foreground process is read on every state tick (100 ms), so a hosted agent registers within a tick of reaching the foreground. A tick that can't read it changes nothing.
  - On each change the state starts over: the pane publishes `unknown` (unless it already was), then whatever the new rules settle on, so the shell's `working` can never turn into the agent's `done`. Input queued for `idle` (§4) or a comment waiting for the agent's prompt (§9) is dropped, so text meant for the agent is never typed into the shell, nor the other way round; a dropped comment stays undelivered.
  - The daemon saves `hosted_agent` to the pane's row, then sends a `changed` pane event (§5).
  - Only `claude` and `codex` are hosted: a rule file for another agent (`rules/aider.toml`) applies to no shell pane.
- **v1 ships rules for `claude` and `codex`,** both from recorded sessions.
- **`claude`** (from Claude Code v2.1.325, recorded at 120×40 in the default inline TUI and in the fullscreen one with a status line; foreground process `claude`, or `node` for some npm installs):
  - The OSC 0 title is a state glyph and the session's name: `✳ Claude Code` at a fresh prompt, then a name Claude Code makes up after the first turn (`✳ Ok`). The glyph is `✳` when idle, a half-circle spinner (`◐`, `◑`) while it thinks, streams or runs a tool, and `✳` again on a permission prompt. The rules read `working` from a spinner (Braille as well, which versions before v2.1.228 drew) and `idle` from `✳`, below the dialog rule.
  - Dialogs are read from the screen by the key hint on the bottom non-blank row (`bottom:1`), which model output can't reach because the footer holds it otherwise: `Enter to confirm · Esc to cancel` under the folder trust dialog (`Accessing workspace:` … `Yes, I trust this folder`) and other select dialogs, and `Esc to cancel · Tab to amend` under a tool permission prompt (`Do you want to proceed?` … `1. Yes`). In the fullscreen TUI the dialog replaces the composer and its hint is still the last non-blank row.
  - The inline footer adds `esc to interrupt` while a turn runs; a rule reads it from the bottom row, for when the title is missing. The fullscreen footer with a status line doesn't show it.
  - No OSC 9;4. OSC 7501 only as a startup probe, `ESC ] 7501 ; ? BEL`, which agentdeck doesn't answer; no state follows it. The rules keep OSC 7501 and 9;4 entries should Claude Code start sending them unprompted.
  - These correct the spike's notes in two places: the title doesn't keep `Claude Code` once a session has a name, and it shows `✳`, not a spinner, on a permission prompt, so only the screen tells blocked from idle. The trust dialog now preselects `No, exit`.
  - After `/exit` it clears the title and prints `claude --resume <session id>`; no rule matches, and the process exit publishes `exited`.
- **`codex`** (from codex-cli 0.169.0, recorded at 120×40; foreground process `codex`):
  - OSC 7501 carries every state: `state=idle` at a fresh prompt, `working` while it thinks, streams or runs a command, `done` when a turn finishes, `blocked` (`kind=permission`) on an approval prompt, and `clear` on exit. The rules map `blocked`, `working`, and `idle`/`done`/`error` straight across.
  - Two dialogs are read from the screen, ahead of OSC 7501, by the key hint on the bottom non-blank row (`bottom:1`), which model output can't reach because the footer holds it otherwise:
    - the approval prompt (`Would you like to run the following command?` … `Press enter to confirm or esc to cancel`), should OSC 7501 not flag it;
    - the folder trust dialog (`Trust this folder?` … `enter continue · esc back`), which comes before any OSC 7501.
  - The OSC 0 title is the folder name, with a Braille spinner in front while working and `[ ! ] Action Required |` in front when blocked. Users can choose what the title shows, so no rule reads it. Codex sends no OSC 9;4.
  - After `/exit` it sends OSC 7501 `clear` and prints `codex resume <session id>`; no rule matches, and the process exit publishes `exited`.
- **Tests:** every rule set has unit tests that feed **recorded terminal output** (`tests/fixtures/<agent>/*.bytes` plus the expected state) through a `Term`.
- **Recording fixtures:** `script/record-pty.py --out DIR --steps FILE -- <argv>` runs the CLI in a 120×40 PTY with `TERM=xterm-256color`, answers the terminal queries a TUI waits on, types what a steps file says (`wait <regex>`, `sleep`, `send`, `mark <name>`, `end`), and writes the raw bytes since each `mark` to `<name>.bytes`, with each mark's foreground process and OSC sequences in `marks.log`. Each fixture continues the one before it, so a test feeds a chain in order. To re-record `codex`, run the `*.steps` files beside its fixtures, each of which names its flags:
  - Run it in a throwaway git repo (`mktemp -d /tmp/agentdeck-codex-XXXXXX`: no `.` in the path, since `-c` splits its key on dots), never a real one, with trivial prompts; it uses the account's quota.
  - Pass everything as flags; don't edit `~/.codex/config.toml`. `-a on-request -s read-only` plus a prompt asking for a command with escalated permissions forces an approval prompt (0.169.0 dropped `untrusted`). `-c 'projects.<dir>.trust_level="trusted"'` skips the trust dialog; the quoted TOML key form doesn't. Record the trust dialog with no flags and end it without answering, since answering saves the choice to `config.toml`.
  - Sleep a second before sending Enter, or Codex takes the text and the Enter as one paste.
  - Wait on text the prompt itself doesn't contain.
  - To re-record `claude`, run its `*.steps` files the same way, each naming its flags, with an allowlisted environment (`env -i PATH=… HOME=… USER=… SHELL=… LANG=…`). Never pass `CLAUDECODE` or `CLAUDE_CODE_*` through from a Claude Code session.
    - `--setting-sources project,local --strict-mcp-config` keeps the user's settings, hooks, plugins, status line and MCP servers out of the recording; `--model haiku` keeps it cheap; `--permission-mode manual` makes a Bash command that writes (`touch a.txt`) ask, since auto mode was on by default and read-only commands like `echo` never ask; `--session-id <uuid>` launches it as agentdeck does.
    - Claude Code has no flag to skip the trust dialog, and answering `Yes, I trust this folder` saves it to `~/.claude.json`. Trust is inherited from a trusted parent folder, but inside a git repo only up to the repo's root, so record the trust dialog in a fresh `mktemp -d` git repo and end it without answering, and record the sessions in a `mktemp -d -p <a folder trusted once>` that isn't a git repo.
    - Wait on single words (`proceed`, `confirm`), since Claude Code moves the cursor between words, and on the title (`\x1b\]0;✳`, `\x1b\]0;(?!✳)`) for a turn's start and end.
  - Scrub before committing: the temp dir's random suffix (also where the renderer split it with a cursor move), session ids (to `00000000-0000-7000-8000-000000000001` for `codex`, `00000000-0000-4000-8000-000000000001` for `claude`), the plan label in Claude Code's banner (to as many `X`s, e.g. `Claude XXX`, so cursor positions hold), and any home path, user, org, email or account name. Render the chain afterwards and check the screens' text too, since the renderer may split a word with cursor moves. Keep the bytes otherwise as recorded; trimming is only cutting a chain's last fixture at a frame end (`ESC [ ? 2026 l`).

## 8. PR sync

- **Token:** the daemon uses the first source that gives one: a **saved token** in the system keyring, then `GH_TOKEN`, else `GITHUB_TOKEN`, from its own environment (empty is the same as unset), then `gh auth token`. The saved token wins because an env var is easier to forget than an app setting. A token GitHub rejects doesn't send the daemon on to the next source.
  - **Re-read:** it reads the sources at start, again after a 401, and again whenever the auth routes (§4) save or delete the token; while there is none, every sync reads them again. Each read checks the token it finds with `viewer { login }`, keeping the login and the `X-OAuth-Scopes` header for `GET /v1/github/auth`, and sends `github_auth` (§5) when the source, login or `rejected` changed. A change through the auth routes also starts a sync at once. No token, or one GitHub still rejects after that re-read, means `GET /v1/prs/status` reports `logged_out` (with `last_error` "GitHub rejected the token" for a rejected one), and the GUI shows a banner (§11); `GET /v1/github/auth` then keeps the rejected token's `source`, with no `login` and `rejected: true`, and sends `github_auth`, also when GitHub accepted the token at the re-read and rejected it on the next request. A saved token stays saved: Sign in with GitHub or a pasted token replaces it, and Sign out deletes it. A check that fails for another reason (GitHub down) keeps the token, and the login GitHub last gave for it.
  - **Credentials** live only in the system keyring, through `keyring-core` and the keyring project's Secret Service store (`zbus-secret-service-keyring-store`), connecting on each call, so a keyring that starts or unlocks after the daemon is found. A call that takes over 10 s (a locked keyring waiting on a prompt) counts as no keyring. The daemon owns it, so PR sync runs while the GUI is closed. The token and the OAuth client ID are never in a file (`config.toml`, `daemon.json`, the database), a log, an error, an event or a response, and never added to a pane's environment: a pane gets only what §6's allowlist passes from agentdeckd's own environment, so a `GH_TOKEN` the user exported reaches it as it reaches their shell, while a saved token or the client ID never does. `last_error` and log lines carry GitHub's message, never a request's headers.
  - **Keyring entries** are under the service `agentdeck`. The token's is named `github.com/<login>`, so a later version can hold more than one account; v1 holds one, and saving a token deletes any other `github.com/` entry. The daemon finds it by searching the service's entries, so no file names the login. The OAuth client ID is a separate entry, `oauth-client-id@github.com` (no GitHub login holds an `@`).
  - **No keyring** (headless, or no Secret Service on the session bus): reading finds no saved token and goes on to the environment. Saving a token or a client ID, and starting a sign-in, is `503 no_keyring`: "No system keyring is running, so agentdeck can't save a token. Set GH_TOKEN in agentdeckd's environment instead."
  - **Pasting a token** (`PUT /v1/github/token`): the daemon checks it with `viewer { login }` before saving. A 401 is `422 invalid_token` ("GitHub didn't accept this token.") and saves nothing; any other failure is `502 github_error`. GitHub's `X-OAuth-Scopes` says what a classic token may do. One without `repo` or `public_repo` still saves, and clients warn "PR sync works; closing PRs needs repo". A fine-grained token sends no scopes header; it saves, and clients note "Closing works only on repos you own". Clients show both from `scopes`, for whichever source gives the token.
- A sync every 120 s (the first at start), and on `POST /v1/prs/sync`, which clients call when a task is opened. One sync runs at a time. `AGENTDECK_GITHUB_API` replaces the GraphQL URL (`https://api.github.com/graphql`); tests point it at httpmock.
  - **Age cutoff:** only PRs GitHub updated in the last `max_age_days` days sync: the setting `pr_sync.max_age_days` (§2), default `90`, `0` for no cutoff. Each sync reads it as it begins, so a PATCH applies to the next sync, and widening it (more days, or `0` where there was a cutoff) starts a full sync at once, after any sync running, so the older open PRs it now lets in arrive without waiting for the hourly full sync. Narrowing it waits for the next sync. `AGENTDECK_PR_MAX_AGE_DAYS` overrides the file (tests use it); empty is the same as unset, and a value that isn't a count of days is logged and ignored. The cutoff is that many days before the sync began.
  - **Full:** the first sync, the first after an hour since the last full one (`AGENTDECK_PR_FULL_SYNC_SECS`, `0` for every sync), and the next one after the age cutoff widens, in two phases. First the list `viewer.pullRequests(states: OPEN)`, 100 a page, most recently updated first, with light fields only (no review, no checks); each page is stored as it arrives, a stored PR keeping its review and checks. The list stops at the first PR updated before the cutoff: neither it nor anything after it is stored, and no later page is read. Then every field, fetched by number, for the PRs that are new, that GitHub updated since they were stored, or that are unsettled (below).
  - **Incremental:** the rest search `is:pr author:@me updated:>=<T>`, where `T` is 10 minutes before the last good sync began, so a merged or closed PR comes back in its new state. A merged or closed PR not stored as open is skipped, and so is any PR updated before the cutoff. Then the unsettled open PRs the search left out, updated within the cutoff, are fetched by number, and inbox PRs are matched to workspaces again as stored; aged-out PRs are left out of both. Nothing is found gone.
  - **Unsettled:** a PR whose checks are `pending` or none (none had started when it was stored), or whose review is `review_required` or `changes_requested`. A check run finishing doesn't update a PR, so the search misses it, and GitHub doesn't document that a review does. No review decision means the repo requires none, and `approved` waits on nobody. Each incremental sync costs one more request per 25 unsettled PRs.
- `POST /v1/prs/sync` answers once its sync finishes, with the same body as `GET /v1/prs/status`: `{ login: "logged_in"|"logged_out", last_synced_at, last_error, progress, max_age_days }`. `max_age_days` is the age cutoff the next sync uses (`0` for none), so clients never read `config.toml` themselves. A failed sync is still 200, with `last_error` set: `GitHub answered <status>`, plus GitHub's `message` when the body is JSON. A request that fails with a 5xx or in transit is tried up to 3 times, 1 s then 2 s apart.
- Each result becomes a PR task, titled with the PR's title:
  - Its **workspace** is the oldest unarchived workspace whose dir holds a clone of the PR's repo with `head_ref` present as a local branch. A clone is a git repo up to 3 levels under the dir (as the dirty report searches) with any `github.com` remote (https, ssh or scp-like URL) naming the repo, compared case-insensitively. If no workspace matches, it goes to the inbox (`workspace_id` NULL). Only an inbox task is matched again on later syncs; sync never moves a PR task out of a workspace.
  - **The user's pick sticks:** once the user sets a PR task's workspace (`PATCH /v1/tasks/{id}` with `workspace_id`, the inbox included), `workspace_picked_at` is stamped and sync never matches or moves the task again. That covers an inbox PR whose clone sits where the match rule doesn't look, and a PR the user wants in the inbox although a clone matches it.
  - **New PR:** a PR task created with status `review`.
  - **Merged or closed:** the task goes to `done`; reopened, back to `review`. While the PR's state holds, the task keeps whatever status it has. In a full sync, PRs that left the list are fetched by number, once; one GitHub no longer shows is stored as closed. Fetches by number go 25 to a request, 4 requests at a time.
  - **Aged out:** in a full sync, a PR stored as open that left the list and was last updated before the cutoff is not fetched. It is aged out instead (`aged_out_at` set), once: its task goes to `done` (a `changed` event, as any status change sends) and stays findable under Show done; a status the user picks after that sticks. Nothing changes on GitHub. When GitHub next shows it within the cutoff, it is no longer aged out and its task goes back to `review`, as a reopened PR's does.
- `checks` and `review` come from `statusCheckRollup` (`ERROR` counts as failure, `EXPECTED` as pending) and `reviewDecision`. Every task in the API carries its PR as `pr` (null for a plain task).
- A sync stores each page as it arrives, and each task it creates or changes gets a `changed` event (§5) then. While it runs, the status's `progress` is `{ prs_done, prs, stage }` (`prs` from the search's count, `0` until the first page answers; `stage` is `listing`, then `details` while reviews and checks are fetched by number), and every change to it sends a `pr_sync` event. Clients show it: "Syncing… 100 of 271 PRs", then "Syncing details…".
- **Sign in with GitHub** is the OAuth device flow, asking for the scope `repo` once.
  - **Client ID:** the user registers an OAuth App on GitHub, with Enable Device Flow on and no client secret. Its client ID is never committed: the user enters it in Settings, and it is saved in the keyring (`PUT /v1/github/client-id`) like the token. `AGENTDECK_GITHUB_CLIENT_ID` gives it while none is saved; a saved one wins, as the token does. With neither, `POST /v1/github/device` is `409 no_client_id`, and clients hide Sign in. `PUT` refuses a blank one, and one shaped like a user code (`^[A-Z0-9]{4}-[A-Z0-9]{4}$`, as `WDJB-MJHT`: the sign-in's code, pasted in by mistake), with `400 invalid_client_id`: "The OAuth client ID is blank." or "That looks like the sign-in code, not a client ID.", and saves nothing. No error or log line names the client ID.
  - **Start:** `POST /v1/github/device` checks that the keyring can save, then asks GitHub for a device code (`POST https://github.com/login/device/code` with the `client_id` and `scope=repo`) and answers `{ user_code, verification_uri, expires_at }`. A refusal (Device Flow off) is `502 github_error` with GitHub's `error_description`, else its `error`. A client ID GitHub doesn't know gets a 404 `{"error":"Not Found"}` with no description, which tells the user nothing, so a 404 or a bare `Not Found` is `502 github_error` with "GitHub doesn't know this OAuth client ID. Check it in Settings → GitHub." `AGENTDECK_GITHUB_OAUTH` replaces `https://github.com`; tests point it at httpmock.
  - **Polling:** the daemon then polls `POST https://github.com/login/oauth/access_token` (`grant_type=urn:ietf:params:oauth:grant-type:device_code`) at GitHub's `interval`, 5 s slower after each `slow_down`. On a token it saves it as a pasted one is (without the scope notes, since it has `repo`), re-reads, and sends `github_auth` with `device: "signed_in"`. `expired_token`, or `expires_at` passing, sends `device: "expired"`; `access_denied`, `device: "denied"`; any other error, `device: "failed"` with GitHub's message. Each of those ends the polling. A poll that fails in transit is tried again at the next interval, until `expires_at`. An `interval` under 1 s counts as 1 s.
  - **Log:** the start, with the code's expiry and the interval, at info; each poll that fails in transit at warn, with why; each `authorization_pending` at debug, with the count so far; and how the sign-in ended, or that it was cancelled (by `DELETE`, or a new `POST`), at info, with the count of polls, pending answers and transit failures. No line carries the client ID, the device code, the user code or the token.
  - **Cancel:** one sign-in runs at a time, so a new `POST` cancels the one before. `DELETE /v1/github/device` cancels it (204, also with none running) and sends no event.
- **Closing PRs** (`POST /v1/prs/close`) closes them only: no comment, no branch delete.
  - Each `task_id` must be a PR task whose PR is stored `open`, aged-out ones included; any other fails with "Not an open PR" and never reaches GitHub. With no token, every one fails with "Not signed in to GitHub".
  - The daemon reads the PRs' node ids by repo and number, 25 to a request as fetches by number go. Then it closes each PR on its own, one at a time, with its own GraphQL `closePullRequest` mutation, since GitHub has no batch close.
  - A PR GitHub closes is stored as `closed`, and its task goes to `done` at once (a `changed` event), with no fetch by number on the next sync.
  - A failure is that PR's alone: its result is `ok: false` with `error`, GitHub's message (a token without write access fails this way, per PR) or why the request failed, and the rest still close. It answers once every PR is tried.

## 9. Comments and instructions

**The task on linking:** a new agent learns its task from its launch prompt (§6). An agent that gets one later is told it the same way, typed in: linking a live agent pane to a task (`PATCH /v1/panes/{id}` with another `task_id` than it had), and an agent starting in a shell pane linked to a task (§3), queue the task as the launch prompt opens with it: `Task: <title>`, `Task id: <id>`, the report-back line, then the body after a blank line when it has one. It is submitted as a comment is (below), once the pane is `idle` or `done` and never into a `blocked` one, ahead of the task's waiting comments.
- Linking a pane to the task it is already linked to tells it nothing again, and unlinking types nothing.
- A shell pane hosting no agent gets nothing typed in. Each agent that starts in it while it is linked is told the task.
- Nothing records that a pane was told: a pane unlinked and linked to the task again is told it again. The task is dropped untyped if the process exits, the hosted agent leaves, or the pane is linked to another task or unlinked, first: an agent relinked before it reached its prompt is told only the task it is linked to now.

**Task comments** are a thread on each task, every comment with its author.
- **Your comments** (no `pane` on create) go to the task's agent:
  - When a live agent pane is linked to the task (a shell pane counts while it hosts an agent, §3), the comment (its body, trailing whitespace trimmed) is submitted into the newest such pane once it is `idle` or `done`, typed as `input` `submit: true` types a message: the body, then Enter in a write of its own (§4). Unlike `input` `when: "idle"`, it never goes into a `blocked` pane, so it can't answer a dialog. It is marked delivered (time and pane) when typed.
  - Otherwise it goes into the next launch prompt for the task (§6).
  - Linking a live agent pane to the task (`PATCH /v1/panes/{id}`) hands it the task's comments still undelivered, oldest first, after the task itself (above), in the same way: each typed once the pane is `idle` or `done`, and marked delivered then. A shell pane linked to a task gets none while it hosts no agent. Once an agent starts in it, it is told the task, and the task's comments still undelivered are handed to it, as on linking, and typed once it is `idle` or `done`; there is no launch prompt, since the user started it. When the agent leaves, the link stays and the pane gets nothing more until an agent is hosted again.
  - **Moving the task** to another workspace or the inbox (`PATCH /v1/tasks/{id}`) unlinks every pane linked to it in another workspace than its new one, live or exited, since a pane links only to a task in its own workspace (§4). A comment held for such a pane goes to the next agent pane linked to the task, as for any pane no longer linked.
  - **A held comment moves on** when its pane can no longer take it: its process exited, its hosted agent left, or it was linked to another task or unlinked (also by moving the task, below). The pane drops it untyped, and it goes to the task's newest other live agent pane, if there is one, to be typed there once that agent is `idle` or `done`; else it waits on the task, undelivered, for the next agent linked to it or the next launch prompt. A pane is checked against its current link right before anything queued for a task is typed, so nothing meant for a task it left is typed into it.
  - A comment reaches one agent at most once. While it waits for a pane's prompt it is held for that pane alone. Linking another agent pane to the task moves it to that pane only if it is the newer of the two (or the holder is no longer linked), so it still goes to the newest agent pane; the pane that lost it never types it. A launch prompt (§6) takes it from a pane holding it. One already typed or prompted is handed to no pane.
  - Yours are seen when written.
- **Agent comments** are written through the CLI or MCP from inside a pane (`pane` on create, from `$AGENTDECK_PANE`, which a shell pane has too, so an agent hosted in it writes as that agent): progress, "blocked on X", "PR opened", a summary when done. A launched agent has the MCP server and its task's id for this (§6); the CLI and the MCP tools default to the task the pane is linked to now (§10). They are never delivered. Each is new to the user (`seen_at` NULL) until `POST /v1/tasks/{id}/comments/seen`, which the GUI calls when the user opens the task; a task's `unseen_agent_comments` counts them.

**Workspace instructions** are standing context for every agent in a workspace ("Push only after 20 green runs").
- Every launch prompt in the workspace carries all of them (§6). They are never consumed: there is no read or unread, and they stay until deleted. They can be edited.
- **Send to agent:** the GUI submits one into a chosen pane at once (`input` with `submit: true`, `when: "now"`: the text, then Enter in a write of its own, §4), as `agentdeck agent send --now` does. The instruction is unchanged.

## 10. CLI and MCP

`agentdeck` (clap) reads `daemon.json` and starts the daemon when it isn't running: no file, a pid that isn't running, a port that refuses the connection, or a daemon that doesn't answer `/v1/health` within 1 s (§2). It starts `$AGENTDECK_DAEMON` if set, else the `agentdeckd` beside its own executable, else `agentdeckd` from `PATH`, in its own process group with no terminal, and waits up to 20 s for a `daemon.json` that answers `/v1/health` (the daemon may first wait for one that is shutting down, §2). Output is human-readable, or with `--json` the API's own objects (`ws rm` prints `{id, deleted}`, `tail` prints `{pane, output}`). A failure prints `agentdeck: <message> (<error_code>)` to stderr and exits 1; `agent new`'s `invalid_argv` prints the message alone (§6).

```
agentdeck ws ls | new <name> [--dir PATH] | rename <ws> <new-name> | archive <ws> | mute <ws> | unmute <ws> | rm <ws> [--force]
agentdeck task ls [--status S] [--ws WS] [--inbox] | add <title> [--ws WS] [--body B] | set <id> --status S | edit <id> [--title T] [--body B] [--ws WS | --inbox] | show <id>
agentdeck comment ls [--task T] | add <body> [--task T]
agentdeck instruction ls [--ws WS] | add <body> [--ws WS] | edit <id> <body> | rm <id>
agentdeck agent new --ws WS [--agent claude|codex] [--cwd DIR] [--task T] | send <pane> <text> [--now] | link <pane> (--task T | --none)
agentdeck pr sync | status | close <id>… [--yes]
agentdeck config ls | get <key> | set <key> <value>
agentdeck daemon restart
agentdeck tail <pane> [--bytes N]
agentdeck mcp            # MCP server over stdio
```

- A `WS` or `<ws>` is a workspace's id, slug or name, tried in that order; a name two workspaces share is an error that lists their slugs.
- `ws new --dir` takes a path relative to the current directory too; the CLI sends it absolute.
- `ws rename` sets a workspace's name with `PATCH /v1/workspaces/{id}` and prints the workspace as `ws ls` does, under its header (`--json`: the workspace). Its slug and dir stay, so the old slug still finds it; a blank name is the daemon's `invalid_name`. MCP has no tool for it.
- `ws rm` without `--force` on a dirty dir prints the dirty report and exits 1.
- `task edit` changes what it is given with `PATCH /v1/tasks/{id}` and needs at least one of `--title`, `--body`, `--ws` and `--inbox`; `--inbox` moves the task out of its workspace and can't go with `--ws`. It prints the task as `task show` does (`--json`: the task). A PR task's title is its PR's, so another `--title` is the daemon's `invalid_title`.
- `agent new` launches the agent with `POST /v1/panes` (no `argv`: the daemon builds it and the launch prompt) in `--cwd`, made absolute, or the workspace's dir. The pane goes in the workspace's first tab with no panes, else in a new tab titled after the agent, and becomes that tab's layout. A tab made for a launch that fails is deleted.
- `agent send` submits the text with `input` `submit: true` (the text, then Enter in a write of its own, §4), with `when: "idle"`, or `"now"` with `--now`.
- `agent link` links a running pane to a task with `PATCH /v1/panes/{id}`, or unlinks it with `--none`; it takes exactly one of the two. It prints `linked <pane> to <task>` or `unlinked <pane>`, and the pane with `--json`. MCP has no tool for it in v1.
- `comment add` run with `$AGENTDECK_PANE` set is authored by that pane's agent, or by the agent the shell pane hosts (§3); otherwise it is yours. `comment ls` prints who wrote each comment (`you` or the agent) and whether yours reached an agent (`delivered` or `waiting`).
- `comment add` and `comment ls` without `--task` work on the task the caller's pane (`$AGENTDECK_PANE`) is linked to now, read with `GET /v1/panes/{id}`. Not `$AGENTDECK_TASK`, which keeps the task the pane was spawned on (§6). Outside a pane it is an error, "name a task with --task: you aren't in an agentdeck pane (no $AGENTDECK_PANE)", and in a pane linked to no task "name a task with --task: your pane isn't linked to a task".
- `config` names a setting by its dotted key (§2). `ls` prints each key and value, and `set` the key it set, adding "(an environment variable overrides config.toml)" to an overridden one; with `--json`, both print the settings object. `get` prints the value alone, or `{key, value}` with `--json`; a key that isn't a setting is an error. `set` sends a value that reads as a number, `true` or `false` as that, anything else as text, and the daemon checks it (`invalid_setting`).
- Every command except `mcp` and `daemon restart` prints one line to stderr, after `agentdeck: `, when the daemon is older than the CLI (§2), then runs as usual: "warning: agentdeck's background service (agentdeckd) is older than this CLI. Run agentdeck daemon restart to use new features; your agents resume after the restart."
- `pr sync` and `pr status` print the status (§8) a line each: `github:` `logged_in` or `logged_out` (whichever source gives the token), `last sync:` its time or `never`, `syncing:` its progress while one runs, and `last error:` while the last one failed.
- `pr close` closes the PRs of the PR tasks it names with `POST /v1/prs/close` (§8). Without `--yes` it first prints "Close N PRs on GitHub? Their repos' owners will see them closed. You can reopen a PR on GitHub." then a line per repo with its count ("  acme/widgets  2 PRs"), and asks `[y/N]` on stderr; anything but `y` closes nothing, prints "Closed nothing" and exits 0. Without `--yes` and with no terminal on stdin, it is an error that names `--yes`. It prints `closed <repo> #<n>` or `failed <repo> #<n>: <error>` per PR, then "Closed 12 of 14" when any failed, and exits 1 then; `--json` prints the results object.
- `daemon restart` restarts the daemon as §2 says (starting one when none runs) and prints `restarted agentdeckd, now pid <pid>`, or `{pid, version, api_version}` with `--json`.
- `instruction` without `--ws` works on `$AGENTDECK_WORKSPACE`, and is an error outside a workspace. `instruction rm` prints `{id, deleted}` with `--json`.

**MCP tools** (rmcp): `tasks_list`, `task_get { id? }`, `task_create`, `task_update { id?, … }`, `task_comments { task? }`, `task_comment { task?, body }`, `instructions_list { workspace? }`, `workspaces_list`, `prs_status`.
- **No tool closes PRs:** agents don't close your PRs. Only the GUI and `agentdeck pr close` do.
- `AGENTDECK_PANE` and `AGENTDECK_WORKSPACE` are set in every pane's environment, and `AGENTDECK_TASK` in one linked to a task when spawned. They are added on top of the allowlist (§6).
- `claude` and `codex` panes get this server registered at launch and on resume (§6); `$XDG_RUNTIME_DIR` from the pane's environment leads it to the same daemon.
- Tools default to the caller's workspace and pane:
  - `tasks_list` lists the caller's workspace unless given a `workspace`; it takes `inbox: true` for the inbox and `all_workspaces: true` for everything. Outside a workspace it lists everything.
  - `task_create` goes to the caller's workspace unless given one.
  - `task_update` moves a task to a `workspace` it is given, or to the inbox with `inbox: true`; given both, it is an error. Without either the task stays where it is.
  - `task_comment` is authored by the caller's pane (its agent, or the agent it hosts), and so never delivered to an agent.
  - `task_get`, `task_update`, `task_comments` and `task_comment` work on the task the caller's pane is linked to now when not given one, as `comment add` does; outside a pane, or in one linked to no task, the tool fails asking to name the task.
  - `instructions_list` lists the caller's workspace unless given a `workspace`; outside a workspace, with none given, it is an error.
- Each tool answers with the API's JSON object as text. A failure (a bad argument, or the daemon's error with its `error_code`) is a tool result with `isError: true`, not a protocol error.
- Each call reaches the daemon the way the CLI does, so a daemon restarted under a long-lived `agentdeck mcp` is found again.

Any other scheme, or another host's file, is refused silently (a debug log line), so a program can't make a click run a custom URL handler.

Anything after the column (`src/main.rs:42:fn main`) isn't part of it. A relative path resolves against the directory the shell last reported with OSC 7 (`file://host/path`, for this host), else the pane's launch dir; `~/` against `$HOME`. Only an existing regular file is a link: no underline and no hand otherwise. A URL or OSC 8 link over the same text wins.

  - **Withdrawn:** a notification still open is closed (`CloseNotification`) once the user can see what it is about: the window is focused while the pane's tab shows, the task sheet is open on the PR task, or the Tasks view shows. Clicking one closes it too, and quitting the GUI closes every one still open, so none outlives the app that could act on it.
  - **One connection:** `agentdeck-notify` holds one session-bus connection for the whole app and one task on GPUI's foreground that sends each `Notify` and reads the server's `ActionInvoked` and `NotificationClosed`, by the id the server gave each notification. A notification left open costs an entry in that id map, never a thread or a connection; it leaves the map once clicked, withdrawn or closed. (GPUI's own `show_system_notification` starts a thread and a connection per notification and holds both until the server closes it, #133.) Without a session bus the GUI logs why once and shows none.
  - **Panes:** an agent pane (not a shell, unless it hosts an agent) turning `blocked` or `done` while the user can't see it: its tab isn't the one shown, its workspace isn't, or the window isn't focused. Title "<Agent> is blocked" / "<Agent> is done"; body "<linked task title, else tab title> · <workspace>". Once per state change, not again while the state holds.
    - **Reattach:** attaching resizes a pane to its view, and an agent redraws on a resize, so a done Claude Code can read working, then done again. For 10 s after a pane attaches (`attached`, §5), it turning back to the state it held then (`blocked` or `done`) notifies nothing: the user heard about that state already, from this GUI or the one before a restart. Another state notifies as usual, and so does the same state after the 10 s.
  - **PRs:** a PR task's checks turning `failure`, or its review turning `approved` or `changes_requested`. Title "Checks failed" / "Approved" / "Changes requested"; body "<repo> #<n> · <title>". Changes are held while a PR sync runs and shown when it ends; more than 3 PRs changed in one sync make one "N PRs changed" whose body lists their "<repo> #<n>". None notifies while the user can see what it is about (Withdrawn, above): its task sheet, or the Tasks view for "N PRs changed".
  - Only changes between two reads count: what the GUI first reads after connecting (a pane already blocked, a check already failing) notifies nothing. A read after `resync` (§5) compares with what the GUI had, so it notifies as any other read does.
  - **Log:** each notification shown is logged at info with its tag (`pane:<id>`, `task:<id>`, `prs`) and title; one left out because what it is about is in view, one left out after a reattach, and one withdrawn, at debug.
  - **Muted:** a muted workspace's panes and PR tasks never notify; an Inbox PR has no workspace, so it always can.
  - **Click:** clicking a notification's body focuses the window and shows what it is about: the pane, in its workspace and tab; the task sheet on a PR task; the Tasks view for "N PRs changed". Notifications offer no buttons.
- **Keymap:** `keymap.rs`, normal app shortcuts, `secondary-` bindings loaded with `KeyBinding::load`.
  - A binding wins over the terminal, so every shortcut is one a shell has no use for, after GNOME Terminal. Plain ctrl-letter, alt-letter, the arrows and the paging keys always reach the pane.
  - Tab and Shift+Tab go to the terminal when it has focus (completion in a shell, claude's mode switch); everywhere else they move focus.
  - Quit `secondary-shift-q`, asking first while agents run (Quitting while agents run, above); next / previous tab `ctrl-pagedown` / `ctrl-pageup` (or `ctrl-tab` / `ctrl-shift-tab`); tab 1–9 `alt-1`…`alt-9`; next / previous pane `secondary-shift-down` / `secondary-shift-up`, in layout order; new shell tab `secondary-shift-t`; split the focused pane with a shell right / down `secondary-shift-e` / `secondary-shift-o` (after Terminator); close it `secondary-shift-w`, asking first while it runs. Closing a tab's last pane closes the tab.
- **Logging:** `tracing`, to `$XDG_STATE_HOME/agentdeck/agentdeck-gui.log` (appended to, beside the daemon's `agentdeckd.log`, §2) and stderr, installed before anything else runs, with GPUI's `log` records bridged in. `RUST_LOG` picks the levels (`RUST_LOG=debug` shows the refused links above); without it, or when it doesn't parse, `info` and above. Without a state dir, or when the file can't be opened, the GUI logs to stderr alone and says why there; logging never stops it from starting.
