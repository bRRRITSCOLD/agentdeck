# agentdeck v1 spec

The decisions behind this spec, and their reasons, are in [the v1 map](https://github.com/bRRRITSCOLD/agentdeck/issues/1). This file is the build contract: what to build, not why. When code and spec disagree, change one of them in the same PR.

## 1. Programs and crates

One Cargo virtual workspace, pinned like rust-packages: GPUI pin, toolchain 1.99.1, edition 2024, resolver 3, inherited lints. Crates live under `crates/`.

| Crate | Kind | Depends on | Notes |
|---|---|---|---|
| `agentdeck-core` | lib | — | Domain types, ids, state rules engine, no IO, no GPUI, no tokio |
| `agentdeckd` | bin | core | tokio, dropshot, rusqlite, portable-pty, alacritty_terminal, keyring-core with the keyring project's Secret Service store (§8) |
| `agentdeck-client` | lib | core | progenitor output from `openapi.json`, checked in, built by `cargo xtask client`; plus `daemon` (find, start or restart the daemon, §2) and `ws` (the `/v1/ws` client, §5), shared by the CLI and the GUI |
| `agentdeck` | bin | core, client | CLI; no GPUI. A current-thread tokio runtime drives the async client. Installed beside `agentdeckd`, so every Pane finds it on its `PATH` (§6) |
| `agentdeck-gui` | bin | core, client, notify, `brrritscold-core-gpui` | GPUI app. A small multi-thread tokio runtime, kept as a GPUI global, drives the client and the socket |
| `agentdeck-notify` | lib | — | The GUI's desktop notifications: the freedesktop notifications D-Bus API over one zbus connection, on zbus's own runtime (no tokio); clicks reach GPUI's foreground (§11) |
| `xtask` | bin | — | `openapi` (regenerate spec), `client` (regenerate client), `ci` |

## 2. Daemon

- **Start:** the GUI or the CLI runs `agentdeckd` detached when it can't reach the daemon in `daemon.json`. The daemon a client starts is its child, so the client reaps it whenever it exits (it stops, crashes or is killed), and a long-lived client such as the GUI never keeps it as a zombie. A zombie pid in `daemon.json` counts as not running. A live pid that doesn't answer `/v1/health` within 1 s (a refused connection, one a sandbox forbids, or no answer in time, as the daemon's own check below) counts as not running only while nobody holds the lock (below), as after its pid was reused. While the lock is held, the client gives that daemon 2 s to exit, as a killed one does while the kernel closes its files, and starts a new daemon once it has; otherwise it starts none, since a second daemon couldn't take the lock, and fails: "agentdeckd is running (pid <pid>) but this process can't connect to 127.0.0.1:<port> (<why>). A sandbox may block local network: let it reach 127.0.0.1, or run agentdeck outside it". That covers a client in a sandbox with no network, loopback included (codex can run its shell commands in one), and a daemon stopped with SIGSTOP, held in a debugger or deadlocked, which still accepts connections but never answers: the client reports it instead of hanging. The client checks the lock by taking a shared lock on it and letting go at once; a lock file it can't open or lock counts as held. An optional systemd user unit is `contrib/agentdeckd.service`. Only one daemon runs per user: it holds a lock on `$XDG_RUNTIME_DIR/agentdeck/lock` until it exits.
  - **Lock taken:** while another daemon holds the lock and the daemon in `daemon.json` answers `/v1/health` (with its token, within 1 s), that one serves, so a new daemon exits 1 at once (`another agentdeckd is running`); a client that started it keeps looking at `daemon.json` for 2 s, in case it lost the race to another client's daemon. While the lock is held with no `daemon.json`, or with one that answers nothing, its holder is shutting down, won the race and doesn't serve yet, or was killed or crashed and is still exiting (it leaves `daemon.json` behind, and holds the lock until the kernel has closed its files). So the new daemon waits up to 10 s for the lock, polling it, then writes its own `daemon.json`. It gives up at once when the daemon in `daemon.json` answers, and exits 1 after 10 s (`the agentdeckd that holds … hasn't exited after 10s`). A client gives the daemon it started 20 s to serve, to cover that wait.
  - **Stop:** on SIGINT or SIGTERM the daemon removes `daemon.json` first, then closes its terminals and its HTTP server and gives queries in flight 500 ms, and releases the lock only as it exits. A client that connects meanwhile (`pkill -TERM agentdeckd`, then the GUI or the CLI) starts a new daemon, which waits for the lock and then resumes the panes; the lock keeps them from being resumed twice.
- **Endpoint:** `127.0.0.1:<random>`. On start it writes `$XDG_RUNTIME_DIR/agentdeck/daemon.json` (mode 0600): `{ "port", "token", "pid", "version", "api_version" }`. Every request, including the WebSocket upgrade, carries `Authorization: Bearer <token>`.
- **API version:** `api_version` is `agentdeck_core::API_VERSION`, an integer. **It is bumped in the same PR whenever a route, a field or a message is added or changed**: an endpoint or its request or response in `openapi.json`, a WebSocket message (§5), a `daemon.json` field. A daemon unit test pins `openapi.json`'s fingerprint to the version, so changing the file without a bump fails; the WebSocket and `daemon.json` types say so in their doc comments.
  - The GUI and the CLI compare it with their own as they connect. A lower one, or none (a daemon from before the field, read as `0`), is a daemon **older than the client**, which may lack what the client asks of it. So is a daemon still running from a binary that has since been rebuilt or reinstalled (`agentdeck_client::daemon::binary_replaced`: Linux shows its `/proc/<pid>/exe` as `<path> (deleted)`), since a fix that doesn't change the API version leaves the API version equal: the GUI shows a banner with **Restart** (§11) and the CLI warns (§10). A newer daemon still serves an older client. Neither ever restarts the daemon on its own, since every running agent is re-spawned: the user chooses when.
  - **Restart** (`agentdeck_client::daemon::restart`) is `kill -TERM <pid>` for the daemon the client reached, and only while `daemon.json` still names it by pid and token (a pid alone may have been reused; once another daemon replaced it, the client just connects to that one). It waits up to 10 s for that process to exit, so its lock is free; then it reaches a new daemon the usual way, starting it. The new daemon resumes the panes (§6).
- **Data:** `$XDG_DATA_HOME/agentdeck/agentdeck.db` (SQLite, WAL), and nothing else: a Workspace has no folder (§3). Scratch folders that agentdeck made for Workspaces before they lost their folders, under `$XDG_DATA_HOME/agentdeck/workspaces/<slug>/`, are left as they are: they may hold work, and nothing reads, reuses or removes them. Config is `$XDG_CONFIG_HOME/agentdeck/config.toml`, which the daemon owns: it reads the file at start, and clients read and change the settings only through `GET` / `PATCH /v1/settings` (§4), so the GUI, the CLI and PR sync share one copy. The file need not exist. The GitHub token and the OAuth client ID are not settings and are never in it: both live in the system keyring (§8).
  - **Settings:** `[appearance] theme` (`system` | `dark` | `light`, default `system`; the GUI's theme, §11), `[pr_sync] max_age_days` (a count of days, default `90`, `0` for no cutoff; an open PR older than that is Finished and leaves within 7 days, §8), `[terminal] file_opener` (a command, default `xdg-open {path}`; what a `secondary`-click on a file path in a pane runs, §11) and `[gui] confirm_quit` (`true` | `false`, default `true`; whether the GUI asks before quitting while agents run, §11). Each is named by its dotted key, `appearance.theme`.
    - `file_opener` is split into words as a shell would split it (`shell-words`) and never run through a shell. One argument after the program must hold `{path}`, the file's absolute path; `{line}` and `{col}` are the line and column the path names, `1` when it names none. A value that is blank, doesn't split (an unclosed quote) or passes no `{path}` is refused (`invalid_setting`), and in the file gives the default.
  - **Reading:** a missing file or key gives the default; a value of the wrong kind gives that key's default; a key the daemon doesn't know is ignored; a file that doesn't parse is logged and every default applies, as a state rule file's is (§7).
  - **Writing:** a PATCH re-reads the file, changes only its keys with `toml_edit`, so every other key, table and comment stays, and writes a temp file beside it that it renames over it, creating the dir if need be. A file that doesn't parse is left as it is: the PATCH is `409 unparsable_config`. A change applies at once, with no restart.
  - **Environment overrides:** `AGENTDECK_PR_MAX_AGE_DAYS` overrides `pr_sync.max_age_days` (§8). (`AGENTDECK_PR_FULL_SYNC_SECS` and `AGENTDECK_PR_FINISHED_SECS`, the sync timings tests shorten, are not settings, §8.) The settings then report the variable's value and list the key in `overridden_by_env`. A PATCH of an overridden key still writes the file and answers 200, but the variable's value stays in use, and the key stays in `overridden_by_env`, until the daemon runs without it.
    - The GitHub variables aren't settings and never show in `overridden_by_env`: `GH_TOKEN` / `GITHUB_TOKEN` give the token and `AGENTDECK_GITHUB_CLIENT_ID` the OAuth client ID, each only while none is saved in the keyring (§8).
- **DB access:** rusqlite on one owned connection behind a `spawn_blocking` actor. Migrations are embedded SQL run by `rusqlite_migration` at start.
- **Fresh start (the domain reset):** before migrations run, a database from before the domain reset, one with a `tasks` table, is renamed with its `-wal` and `-shm` files to `agentdeck.db.pre-domain-reset` beside it (a name already taken gets `.2`, `.3`, …, so nothing is overwritten). The daemon logs where it went at warn and starts with an empty database: nothing is upgraded, so the old workspaces, panes and PRs stay in that file, and panes from before don't resume. The check opens the old file read-only, so its WAL moves as it is. Scratch folders under `workspaces/` are left untouched: they may hold work. This is the only reset code; it can go once every install has moved.
- **Logging:** `tracing`, to `$XDG_STATE_HOME/agentdeck/agentdeckd.log` and stderr. The GUI logs to its own file beside it (§11).

## 3. Data model

Ids are UUIDv7 strings, but for a Repository's, which is GitHub's numeric repository id. Times are RFC 3339 UTC strings; the daemon stamps them to the microsecond (`2026-11-14T10:00:00.123456Z`), so they sort as text and an edit right after a create still stamps later.

```sql
CREATE TABLE workspaces (           -- a name, the Repositories it links and its Panes; no folder
  id TEXT PRIMARY KEY,
  slug TEXT NOT NULL UNIQUE,         -- from the name at creation, made unique; the CLI finds it by it (§10)
  name TEXT NOT NULL,
  muted INTEGER NOT NULL DEFAULT 0,  -- notifications
  archived_at TEXT, created_at TEXT NOT NULL
);
CREATE TABLE tabs (
  id TEXT PRIMARY KEY, workspace_id TEXT NOT NULL REFERENCES workspaces ON DELETE CASCADE,
  title TEXT NOT NULL, position INTEGER NOT NULL,
  layout TEXT NOT NULL               -- JSON split tree: {"pane":id} | {"split":"h"|"v","ratio":f,"a":…,"b":…}; JSON null until the tab has a pane
);
CREATE TABLE panes (
  id TEXT PRIMARY KEY, tab_id TEXT NOT NULL REFERENCES tabs ON DELETE CASCADE,
  kind TEXT NOT NULL,                -- 'agent' | 'shell'
  agent TEXT,                        -- 'claude' | 'codex' | 'other' (agent panes)
  hosted_agent TEXT,                 -- 'claude' | 'codex' while a shell pane hosts that agent (§7); NULL otherwise
  argv TEXT NOT NULL,                -- JSON array, as launched (without resume flags)
  cwd TEXT NOT NULL,                 -- the folder it launched in
  folder TEXT,                       -- its last known current folder (§6); NULL: `cwd`, where it launched
  session_id TEXT,                   -- chosen by agentdeck at launch (claude) or discovered (codex)
  state TEXT NOT NULL DEFAULT 'unknown', -- working|blocked|done|idle|unknown|exited
  title TEXT NOT NULL DEFAULT '', exit_code INTEGER, created_at TEXT NOT NULL
);
CREATE TABLE repositories (          -- a GitHub repository a Workspace links or a kept PR belongs to (§8); deleted once neither does
  id INTEGER PRIMARY KEY,            -- GitHub's id (`fullDatabaseId`, REST's `id`), which a rename or a transfer keeps
  full_name TEXT NOT NULL,           -- owner/name, as GitHub calls it now
  url TEXT NOT NULL,
  private INTEGER NOT NULL, archived INTEGER NOT NULL,
  unreachable_at TEXT                -- when GitHub stopped showing it to the sign-in; NULL while it can see it
);
CREATE TABLE links (                 -- a Workspace's tie to a Repository, made by the user
  workspace_id TEXT NOT NULL REFERENCES workspaces ON DELETE CASCADE,
  repository_id INTEGER NOT NULL REFERENCES repositories,
  PRIMARY KEY (workspace_id, repository_id)
);
CREATE TABLE pull_requests (         -- a pull request PR sync keeps (§8), named by its Repository and number
  repository_id INTEGER NOT NULL REFERENCES repositories,
  number INTEGER NOT NULL,
  title TEXT NOT NULL, url TEXT NOT NULL,
  state TEXT NOT NULL,               -- open|merged|closed
  draft INTEGER NOT NULL,
  head_ref TEXT NOT NULL,            -- the branch it merges from
  base_ref TEXT NOT NULL,            -- the branch it merges into
  author TEXT,                       -- the GitHub login that opened it; NULL once that account is gone
  checks TEXT,                       -- pending|success|failure|NULL
  review TEXT,                       -- approved|changes_requested|review_required|NULL
  updated_at TEXT NOT NULL,          -- GitHub's
  synced_at TEXT NOT NULL,
  finished_at TEXT,                  -- when it became Finished (§8); NULL while open within the age cutoff
  unreachable_at TEXT,               -- when a full sync found the GitHub sign-in can't see it (§8); NULL otherwise
  PRIMARY KEY (repository_id, number)
);
CREATE TABLE pr_sync (               -- at most one row
  id INTEGER PRIMARY KEY CHECK (id = 1),
  synced_as TEXT NOT NULL            -- the GitHub login of the last good PR sync (§8)
);
```

**Migrations:** `0001` creates the schema as the domain reset left it, with each Workspace's folder (`dir`, an absolute path, and `dir_owned`, whether agentdeck made it as a scratch folder). The domain reset squashed every earlier migration into it (they made `notes`, then `comments` and `instructions`, `tasks` with their PR rows keyed by task, and added each column above in turn); a database from before it isn't migrated but moved aside (§2). The removed code and migrations are in the tag `pre-domain-reset`. `0002` drops `dir` and `dir_owned`, keeping every Workspace with its tabs, Panes and Links, and touches nothing on disk: scratch folders stay (§2).

A **Workspace** is a name, the Repositories it links (possibly none) and its Panes. It has **no folder**: no scratch folder and no attached one. Its Panes start where the client says (§6, §11) and work in whatever folder they move to, so its agents can work in any repo. Creating, renaming, archiving or deleting a Workspace makes, moves or removes nothing on disk.

A shell pane **hosts** an agent while one the user started in it by hand (`claude`, `codex`) is its foreground process (§7). `kind` stays `shell`; `hosted_agent` names the agent while it runs and is NULL again once it leaves the foreground, when the daemon starts, and when the pane exits. An agent pane never hosts one. Wherever this spec speaks of a pane's agent, a hosting shell pane's is its `hosted_agent`, and "an agent pane" includes it while it hosts one, unless it says otherwise.

A pane's **current folder** is where it works now (§6): `cwd` stays the folder it launched in, and `folder` holds the last folder the daemon read for it, kept after its process exits. Every pane in a response carries it as `folder`, `cwd` when `folder` is NULL.

An agent pane runs its agent only until its process exits. An exited agent pane keeps `kind` and `agent`, so it can be restarted (`POST /v1/panes/{id}/respawn`, §4). An agent pane that comes back as a shell (§6), or that the user turns into one, **becomes a shell pane**: `kind` `shell`, `agent` and `session_id` NULL, `argv` the shell. It keeps its `cwd`.

A **Repository** is a GitHub repository a Workspace links or a kept PR belongs to, named for good by GitHub's id: a rename or a transfer changes its `full_name` and `url`, never which Repository it is, so its PRs and every Link follow its name (§8). It holds only what GitHub says of it, and `unreachable_at` (nothing sets it yet; the sync of linked Repositories that will is tracked in [#362](https://github.com/bRRRITSCOLD/agentdeck/issues/362)).

A **Pull request** row is named by its Repository's id and its number, and has no name of its own: it is listed under its Repository's `full_name` now. Nothing is unique on the name, so a renamed Repository's PRs and those of another Repository that took its old name are different rows, even before PR sync has seen the rename.

A **Link** ties one Workspace to one Repository, at most once per pair; the user makes it (§4, §10), and it goes with its Workspace. A Repository row exists while a Link or a kept PR names it: linking a Repository agentdeck doesn't know stores it, as GitHub shows it (§8), and the daemon deletes it once neither names it, when its last Link goes (by an unlink or with its Workspace) and no kept PR belongs to it, or when PR sync deletes its last PR and no Link names it (below). An archived Workspace keeps its Links.

A PR is **Finished** (`finished_at` set) while it is merged or closed, or open but not updated within the age cutoff (§8). PR sync deletes it 7 days after it became Finished, then deletes its Repository when no Link and no kept PR references it any more, as an unlink does (§4).

v1.1 adds `channels`, `channel_members` and `messages` in their own migration.

## 4. HTTP API (`/v1`, dropshot)

`openapi.json` is generated by `cargo xtask openapi` and committed. A unit test fails when it differs from what the code generates. Errors use dropshot's `HttpError`, and an expected domain failure is its own status with a `code` field (`error_code`): `unauthorized` 401, `not_found` 404, `exited` 409 (input to, or a stop of, a pane whose process has exited), `no_agent` 409 (a stop of a shell pane hosting no agent), `unparsable_config` 409 (a settings PATCH while `config.toml` doesn't parse), `no_client_id` 409 (a sign-in with no OAuth client ID, §8), `invalid_token` 422 (a token GitHub doesn't accept, or a blank one), `not_signed_in` 409 (a Repository lookup with no GitHub token, or one GitHub rejects, §8), `github_error` 502 (GitHub refused a sign-in, couldn't check a token or failed a Repository lookup; the message is GitHub's or why the request failed), `no_keyring` 503 (no Secret Service to save a token or client ID in), and 400 for `invalid_setting` (a key that isn't a setting, or a value it can't take; the message starts with the dotted key), `invalid_name`, `invalid_dir` (a pane's `cwd`), `invalid_layout`, `invalid_target`, `invalid_argv`, `invalid_client_id` (a blank OAuth client ID, or one shaped like a sign-in code), `unsupported_kind`, `unknown_workspace`, `unknown_tab`, `unknown_pane`, `unknown_repository` (a Repository GitHub doesn't show the sign-in: "GitHub can't see owner/name. Check the name or your token's access."). A route or method the daemon doesn't have is dropshot's own 404 or 405 with no `error_code`; every domain failure has one, so the client reads a code-less 404 or 405 as a daemon older than itself (§2) and says "agentdeck's background service is older than this app and can't do this yet. Restart it to use new features; your agents resume after the restart.", never a bare "Not Found". Every route takes a request body of up to 1 MiB (1,048,576 bytes), set once for the server (dropshot's default is 1 KiB); a larger body is dropshot's own 400 with no `error_code` and the message "request body exceeded maximum size of 1048576 bytes", and changes nothing. Every endpoint below is in v1.

Every pane in a response (`POST` and `GET` on `/v1/panes`) carries `hosted_agent`: `claude` or `codex` while a shell pane hosts that agent (§3, §7), else null. It came with `API_VERSION` 6. Every pane also carries `folder`, its current folder (§3, §6), an absolute path; it came with `API_VERSION` 18.

`API_VERSION` 24 let a Workspace's create and update carry its Links (§11 Edit workspace and New workspace): `POST /v1/workspaces` takes `link`, and `PATCH /v1/workspaces/{id}` takes `link` and `unlink`, beside `name` and `muted`. An older daemon ignores both fields, so the GUI's Restart banner (§2) comes first.

`API_VERSION` 23 took the Workspace's folder away (§3): every Workspace lost `dir` and `dir_owned`, `POST /v1/workspaces` its `dir` (an older client's is ignored, and makes no folder), and the dirty report route (`GET /v1/workspaces/{id}/dirty`) and `DELETE /v1/workspaces/{id}`'s `force` went (an older client's `force` is ignored). An older CLI's `ws rm` without `--force` deletes at once.

`API_VERSION` 22 removed the task routes (`/v1/tasks`, `/v1/tasks/{id}`), the pane's task link (`PATCH /v1/panes/{id}` and the pane's `task_id`) and the `task` change event (§5), and added the `pull_request` change event. The GUI calls none of them; an older CLI's `task` commands and `agent link` get the daemon's code-less 404.

| `POST /v1/panes/{id}/stop` | stop the pane's agent and keep the pane: its row, layout place and `session_id` stay. In an agent pane, its process gets the kill `DELETE` sends (SIGHUP to its process group and the foreground one, then SIGKILL after 3 s), and the pane reads `exited` once it has exited (§7), so **Restart agent** (`respawn` with `run: "agent"`) resumes its session later and a restarting daemon doesn't resume it (§6). In a shell pane hosting an agent (§7), only the hosted agent stops: its process group, the foreground one, gets SIGHUP, then SIGKILL after 3 s if it is still in the foreground; the shell keeps running and `hosted_agent` goes back to null. 204 once the signal is sent; the `state` and `exit` events (or `changed` for the hosted agent) follow. 409 `exited` when the process has already exited, 409 `no_agent` for a shell pane hosting no agent (the shell isn't stopped). It came with `API_VERSION` 12 |
| `POST /v1/panes/{id}/input` | `{text, when: "now"|"idle", submit}` (`now` and `false` by default): without `submit`, typed into the PTY as is. With `submit: true`, `text` is a message, typed in two writes: `text` (trailing newlines are the caller's to trim) as one bracketed paste (`ESC[200~…ESC[201~`, any ESC in it removed) when the pane's program has bracketed paste on (DECSET 2004, as the daemon's `Term` tracks it), else as is; then Enter (`\r`) as a write of its own, 200 ms later, followed by another 200 ms before anything else is typed. Claude Code and Codex take text arriving with its Enter in one read as a paste and keep the Enter as a newline, so `text` ending in `\r` without `submit` is never submitted there. `idle` queues until the pane is idle, done or blocked, and is typed at once if it already is. 202 `{queued}`. Queued text is dropped if the process exits, or when an agent starts or stops being hosted in a shell pane (§7) |
| `GET /v1/panes/{id}/tail?bytes=` | raw output tail (256 KiB ring) for `agentdeck tail`, as `application/octet-stream`; all of it without `bytes` |
| `GET /v1/prs?repository=&workspace=&finished=` | the pull requests PR sync keeps, each a `PullRequest`: `reference` (`owner/name#123`, by its Repository's name now), `number`, `repository` (`{ id, name, url, private, archived }`: GitHub's id, `owner/name`, its page, and whether it is private and archived), `title`, `url`, `state`, `draft`, `head_ref`, `base_ref`, `author` (the login that opened it, null once that account is gone), `checks`, `review`, `updated_at` (GitHub's), `unreachable` and `finished` (Finished, §8; it came with `API_VERSION` 20, and a client reads its absence as false), as last synced (§8). Ordered by Repository name ignoring case, then number. Finished PRs are left out unless `finished=true` (`API_VERSION` 20; an older daemon ignores it and lists every kept PR). `repository` (`owner/name`, or its GitHub URL) keeps only that Repository's, by the name GitHub gives it now, ignoring case: none for a name agentdeck doesn't know. Text that names no Repository is dropshot's own 400. `workspace` (an id) keeps only the PRs of the Repositories that Workspace links (from `API_VERSION` 19); one that doesn't exist is `unknown_workspace`. Given both, a PR must pass both. It came with `API_VERSION` 16 |
| `POST /v1/prs/sync?full=` | sync now, after any sync running; with `full=true` the sync is full whatever sync is due (§8; it came with `API_VERSION` 14, and an older daemon ignores it). `GET /v1/prs/status` reports whether GitHub accepts the token (§8), the last sync, the age cutoff and `synced_as`, the login the last good sync ran as (it came with `API_VERSION` 15; absent before any sync GitHub named a login for) |
| `POST /v1/prs/close` | close PRs on GitHub (§8), named by reference: `{ prs: ["owner/name#123", …] }` → `{ results: [{ pr, ok, error? }] }`, one result per reference in the order asked, each `pr` the reference asked for, in `owner/name#123` form; 200 even when some failed. A PR's GitHub URL works as a reference too. Text that names no PR is dropshot's own 400 and closes nothing. It took task ids before `API_VERSION` 16 |
| `GET /v1/github/auth` | where the GitHub token comes from (§8): `{ source: "keyring"\|"env"\|"gh"\|"none", env_var?, login?, scopes?, rejected, client_id_set }`. `env_var` names `GH_TOKEN` or `GITHUB_TOKEN` whenever one is set, also while a saved token overrides it; `login` and `scopes` come from GitHub's answer to the token, `scopes` from `X-OAuth-Scopes` and absent for a token that sends none (fine-grained); `rejected` is true while GitHub rejects the token `source` gives, so a token GitHub couldn't be asked about (no `login` either) is never mistaken for one it refused (it came with `API_VERSION` 9; a client reads its absence as false); `client_id_set` is true while the keyring or `AGENTDECK_GITHUB_CLIENT_ID` gives a client ID. It never carries the token or the client ID |
| `PUT /v1/github/token`, `DELETE /v1/github/token` | PUT `{token}` checks a pasted token with GitHub and saves it in the keyring (`422 invalid_token`, `503 no_keyring`, `502 github_error`); DELETE deletes the saved token (sign out). Both answer as `GET /v1/github/auth` |
| `PUT /v1/github/client-id`, `DELETE /v1/github/client-id` | write-only: PUT `{client_id}` saves the OAuth client ID in the keyring (`invalid_client_id` for a blank one or a sign-in code, §8; `503 no_keyring`); DELETE deletes it. Both answer as `GET /v1/github/auth`; no route reads the client ID back |
| `POST /v1/github/device`, `DELETE /v1/github/device` | start a sign-in with GitHub (§8): `{ user_code, verification_uri, expires_at }` (`409 no_client_id`, `503 no_keyring`, `502 github_error`); how it ends comes as a `github_auth` event (§5). DELETE cancels it, 204 |
| `GET /v1/settings`, `PATCH /v1/settings` | every setting (§2) by section, `{appearance: {theme}, gui: {confirm_quit}, pr_sync: {max_age_days}, terminal: {file_opener}, overridden_by_env}`; PATCH takes a partial object of the same sections (`{"pr_sync": {"max_age_days": 30}}`), writes `config.toml` and answers with every setting |
| `GET /v1/ws` | the WebSocket, §5. Not in `openapi.json`: clients use `agentdeck_core::ws` over their own WebSocket client |

## 5. WebSocket (`/v1/ws`)

One connection per client.
- **Binary frames** carry terminal bytes: `[u32 channel, big-endian][bytes]`. Client → daemon is PTY input; daemon → client is a snapshot or live output.
- **Text frames** are JSON tagged with `t`.

Client → daemon:
```json
{"t":"attach","pane":"<id>","channel":3}
{"t":"detach","channel":3}
{"t":"resize","channel":3,"cols":120,"rows":40}
{"t":"primary","channel":3}
```
Daemon → client:
```json
{"t":"attached","channel":3,"pane":"<id>","cols":100,"rows":30,"title":"✳ Claude Code","state":"idle"}
{"t":"resize","channel":3,"cols":120,"rows":40}
{"t":"title","channel":3,"title":"◐ Claude Code"}
{"t":"state","pane":"<id>","state":"working"}
{"t":"exit","pane":"<id>","code":0}
{"t":"changed","entity":"pull_request","id":"1296269#7"}
{"t":"changed","entity":"repository","id":"1296269"}
{"t":"github_auth","device":"signed_in"}
{"t":"lagged","channel":3}
{"t":"resync"}
{"t":"error","channel":3,"code":"not_found","message":"…"}
```
The message types are `agentdeck_core::ws::{ClientMessage, ServerMessage}`.
- **Attach:** the daemon sends `attached`, then one binary frame holding the **snapshot**, then live bytes. The snapshot and the live subscription are taken under one lock, so no output is lost or doubled.
  - The snapshot is the daemon's `Term` re-encoded as escape sequences (SGR runs, cursor, modes). It includes scrollback and the primary screen under an alternate screen.
  - The client feeds it into a fresh `alacritty_terminal::Term` of the `attached` size. It starts with a full reset, so a reused `Term` works too.
  - It does not carry the scroll region, tab stops or the active character set, which `alacritty_terminal` keeps private.
  - It ends with the shell's last OSC 7 (`ESC ] 7 ; <uri> ST`), which a `Term` ignores, so a client reading OSC 7 for file paths (§11) has the directory from the attach on. Nothing else changes: an older client's `Term` drops it. The same OSC 7 is the first source of the pane's current folder (§6).
  - Attaching a channel that is already attached replaces it.
- **Resize:** the **primary** client's size wins. The most recent client to send `primary` (the focused GUI window) is primary; until one does, or after it detaches, any client's resize applies. A resize from any other client is ignored and answered with `resize` carrying the size the pane keeps. Sending `primary` applies the size that client last asked for. Other attached clients get `resize` when the size changes; bytes after it were written at the new size.
- **Terminal queries** (DA, cursor position, …) are answered only by the daemon's `Term`. Clients drop the replies their own `Term` generates.
- **Backpressure:** a client more than 1 MiB behind on a channel gets `lagged`. It then re-attaches for a fresh snapshot.
- **Data events:** `changed` tells clients to refetch an entity over REST: `workspace`, `tab` or `pane`, after it is created, changed or deleted (a pane also when an agent starts or stops being hosted in it, §7, and when its current folder moves, §6); `pr_sync` (id `status`) means `GET /v1/prs/status`, when a PR sync begins, reads a page or ends, or a PATCH changes the age cutoff; `settings` (id `settings`) means `GET /v1/settings`, after every PATCH; `repository` (id GitHub's repository id) means `GET /v1/repositories` and `GET /v1/prs`, when PR sync or a lookup stores a Repository it didn't have or GitHub renamed, transferred or otherwise changed one (§8), when a Link to it is added or removed, the Repository deleted with it included (§4), and when PR sync deletes it once no Link and no kept PR references it (§8; it came with `API_VERSION` 16, and an older client skips it); `pull_request` (id its Repository's GitHub id and its number, `1296269#7`, so a rename keeps it) means `GET /v1/prs`, when PR sync stores a PR it didn't have, stores one changed, marks one unreachable or Finished, or deletes one, and when a close from agentdeck stores one closed (§8; it came with `API_VERSION` 22, replacing `task`, and an older client skips it); a Link change sends `workspace` for its Workspace after it. `state` and `exit` are sent to every client, attached or not. The daemon subscribes a connection to these events before it answers the upgrade, so every event published after the client sees the 101 reaches it.
- **Resync:** a connection that falls more than 1024 events behind misses some. It gets `resync` in their place (and the daemon logs it at info), then the events after. A client reads everything it shows again over REST, as on a `changed` for each entity, and compares what it reads with what it had, so a change made meanwhile still notifies (§11).
- **GitHub auth:** `github_auth` means `GET /v1/github/auth` (§8), sent to every client after a token or client ID is saved or deleted, after a re-read changes the token's source, login or `rejected`, when PR sync finds GitHub rejecting a token it accepted a moment ago, and when a sign-in ends. Only then does it carry `device`: `signed_in`, `expired`, `denied`, or `failed` with GitHub's `message`. It never carries the token, the client ID or the user code.
- **Errors:** a message the daemon can't act on gets `error` with a `code`: `not_found` (attach to a pane that isn't live), `not_attached` (a channel with nothing attached), `invalid_message`.

## 6. Launching agents

- **Environment:** built from an allowlist: `PATH HOME USER SHELL LANG LC_* TERM COLORTERM XDG_* SSH_AUTH_SOCK GH_* EDITOR CODEX_HOME CLAUDE_CONFIG_DIR`, plus `TERM=xterm-256color` and `COLORTERM=truecolor`. Nothing else from the daemon's own environment is passed on, and that rule is tested. On top: `AGENTDECK_PANE` and `AGENTDECK_WORKSPACE` in every pane, and nothing else of agentdeck's (`AGENTDECK_TASK` went with tasks).
- **`PATH`:** every Pane's `PATH` is the daemon's, with the folder holding the running `agentdeckd` (its executable's folder, from `/proc/self/exe`) appended at the end, so `agentdeck`, installed beside `agentdeckd`, resolves in every Pane without shadowing anything earlier on the user's `PATH`. With no `PATH` of its own the daemon gives Panes that folder alone; a folder holding a `:` can't be a `PATH` entry, so the daemon logs it at warn and leaves `PATH` as it was. Agents learn about agentdeck through this CLI, not an MCP server.
- **Where a pane starts:** in the folder the client names (`POST /v1/panes` `cwd`), since a Workspace has none (§3): the GUI's is the focused Pane's current folder, else `~` when the Workspace has no Pane (§11); `agent new`'s is `--cwd` or the CLI's own current folder (§10). A resumed pane starts in its last known folder (below).
- **Argv by agent:** `claude` and `codex` are looked up on the pane's `PATH`, so tests put stubs first.
- **A program that can't start** is refused with 400 `invalid_argv` and the pane row is dropped. When `argv[0]` is a bare name in none of the pane's `PATH` directories, the message is only what to do: "`codex` isn't on agentdeckd's PATH. Install it, or start agentdeckd from a shell where it's found."; the lookup's whole error, which lists every `PATH` directory, goes to `agentdeckd.log` at warn. Any other spawn error keeps its text. The GUI's toast and `agentdeck agent new` show an `invalid_argv` refusal as that message alone.
  - `claude`: `claude --session-id <uuid>`, with a UUIDv4 agentdeck chooses.
  - `codex`: `codex`. Codex has no flag to start on a chosen session id (checked against `openai/codex` on 2026-11-11: `codex resume <id>` and `codex fork <id>` only). It writes each session to `$CODEX_HOME/sessions/YYYY/MM/DD/rollout-<timestamp>-<uuid>.jsonl` (`CODEX_HOME` from the pane's environment, default `$HOME/.codex`). The daemon lists those files just before launch, then polls every 250 ms for up to 2 min, while the pane runs, for the newest new one whose id no other pane holds, and stores its id as `session_id` (a `changed` pane event follows).
  - `other` and `shell`: argv as given.
  - `panes.argv` holds the argv as first launched.
- **No launch prompt:** agentdeck starts every agent with no prompt and tells it nothing of its own. An agent reads its CLAUDE.md or AGENTS.md as it always does; work reaches it when you paste it in or `agentdeck agent send` submits it (§10).
- **Trust dialog:** never answered automatically: agentdeck types nothing into a pane on its own (§9). The GUI focuses the new pane so you can answer it.
- **Current folder:** a pane's current folder is the folder its shell last reported with OSC 7 (`ESC ] 7 ; file://<host>/<path> ST`, percent-decoded; a `<host>` that is neither empty, `localhost` nor this machine's hostname is ignored), else its process's working directory as Linux reports it (`/proc/<pid>/cwd`, while the process runs; a removed folder reads as its old path), else the one last known, which starts as the folder it launched in. The daemon keeps it as the pane's `folder` (§3), returns it on every pane, keeps it after the pane exits and sends `changed` for the pane when it moves. It reads it:
  - on the state timer's tick (§7) after the pane printed, at most once a second while it keeps printing (a `cd` ends with a prompt), and never while the pane is quiet, so an idle pane costs nothing;
  - on every `GET /v1/panes/{id}` (§4), so `agentdeck agent ls` and a client's reread get it as it is;
  - as the process exits, from its last OSC 7 only, since its working directory can't be read once it is gone;
  - as the daemon stops (§2), for every pane before its process ends, so a pane resumes where it was.
  A shell that sends no OSC 7 (`sh`, `bash` without a prompt hook) is followed through `/proc`; one that does (fish, or a prompt hook such as VTE's `vte.sh`) is followed through it, and its report wins. macOS has no `/proc`: there only OSC 7 moves a pane.
- **Resume after a restart:** at start, before it serves, the daemon re-spawns each pane whose state isn't `exited`. Exits aren't recorded while the daemon shuts down, so those are the panes that were alive; an agent pane stopped (`POST /v1/panes/{id}/stop`, §4) whose process hasn't exited yet, inside its 3 s kill grace, is recorded as exited as the shutdown begins instead (no exit code), so it isn't one of them. Their rows, and so the layout, are unchanged.
  - `claude` panes as `claude --resume <session_id>`.
  - `codex` panes as `codex resume <session_id>`; one whose session was never found comes back as a shell.
  - **A resume that fails at once starts fresh**, at start and on `POST /v1/panes/{id}/respawn` (§4) alike: a resumed `claude` or `codex` that exits non-zero within 10 s is taken for one that can't find its session: Claude Code prints "No conversation found with session ID: <id>" and exits 1 at once, and Codex prints "ERROR: No saved session found with ID <id>. …" and exits 1 within a second (codex-cli 0.169.0, checked on 2026-11-17), rather than showing it in a TUI that stays open. The exit is what counts, not the message, so a resume that fails another way at once starts fresh too. The daemon logs it at info and starts the agent again in the pane as a new pane starts (above): a new session (stored as `session_id`) and no prompt. It does so once per resume: the fresh start isn't watched, so an agent that fails either way stays exited, and a clean exit (`0`), a pane closed or stopped (§4) meanwhile or a daemon stopping starts nothing.
  - Each pane starts in its last known `folder` (§3), else, once that folder is gone, in the daemon's `$HOME` (`~`), which then becomes its `folder`. Claude Code finds a session by the folder it started in, so a `claude` pane resumed elsewhere starts fresh (below).
  - All other panes as `$SHELL` (else `/bin/sh`) in that folder, with the `shell` rules and hosting on (§7), so an agent the user starts there is hosted. An agent pane that comes back this way (a `codex` pane whose session was never found, an `other` agent's) becomes a shell pane (§3), saved before it starts. A shell pane that hosted an agent comes back as that shell alone: the hosted agent isn't resumed, and `hosted_agent` is NULL until the user starts one again.
  - A pane that can't be re-spawned (its folder and `$HOME` both gone, say) is marked exited.
  - A pane that had exited stays exited, a stopped one (`POST /v1/panes/{id}/stop`, §4) included, even when the daemon stopped before its agent had.

## 7. Agent state

`agentdeck-core::state` evaluates **rules**: data files, embedded defaults that a file in `$XDG_CONFIG_HOME/agentdeck/rules/<agent>.toml` can override. A file that doesn't parse is logged and the defaults apply. Shell panes read `rules/shell.toml`; none is shipped, so a shell is `working` while a command it runs prints and `unknown` otherwise. Inputs are the foreground process name, the OSC 0/2 title, the last N screen rows, OSC 9;4 and OSC 7501, and time since the last output.

```toml
agent = "claude"
process = ["claude"]

[[rule]]                       # first match wins
state = "blocked"
rows = "bottom:1"
contains = ["Esc to cancel"]

[[rule]]
state = "working"
title_regex = '^[◐◓◑◒]'

[[rule]]
state = "idle"
title_regex = '^✳'

[settle]
min_ms = 400                   # a new state must hold this long before it is published
```

- **Rule keys:** a rule names a `state` (`working`, `blocked` or `idle`) and one or more conditions, all of which must hold:
  - `title_regex`, matched against the title;
  - `contains`, strings that must each appear in `rows`, which is `screen` (the default) or `bottom:N`, the last N non-blank rows of the live screen;
  - `progress`, OSC 9;4 states (`removed`, `normal`, `error`, `indeterminate`, `paused`);
  - `program_status`, OSC 7501 states (`idle`, `working`, `done`, `blocked`, `error`).
  The rules apply only while a `process` entry is in the foreground, or when the foreground process can't be read. `done`, `unknown` and `exited` come from the evaluator, never from a rule.
- **done vs idle:** `done` is published when a pane goes working → idle. It turns back to `idle` once the pane is focused, or after a new prompt.
- **Exit:** a dead process is `exited`, whatever the rules say. The daemon waits on each pane's process rather than on its PTY, since a child it leaves running (a background job, an MCP server) keeps the PTY open. Once the process has exited, the pane is exited as soon as its PTY closes, or 1 s later if something still holds it; then every process left in the pane's session gets SIGHUP, and so does every process holding the PTY's slave (`/dev/pts/N`, found through `/proc/<pid>/fd`), which reaches a child that started a session of its own (`setsid`). Whatever still holds the PTY 1 s after that gets SIGKILL, so the PTY always closes and the pane's reader ends, whether the pane is then closed, respawned or left exited. The daemon saves the exit to the pane's row before anything reports it: the `state` `exited` and `exit` events and `GET /v1/panes/{id}` show it only once the row says `exited`, so archiving the workspace right after is never refused for that pane (`panes_running`). A resumed `claude` or `codex` that exits non-zero within 10 s is started again afresh, once (§6): the pane shows `exited` for that moment, then starts over at `unknown`.
- **No match:** the state is `unknown`, unless the pane has produced output in the last 2 s, in which case it is `working`. Output within 300 ms of a resize is a redraw and doesn't count. In a shell pane, neither does output before anything is typed into it (its prompt, what its rc files run), nor output while the shell itself is the PTY's foreground process, running no command (its prompt, the echo of what is typed at it). The foreground is read on every state tick (100 ms); once the shell is back in front, what a command printed before it doesn't count either. So a shell stays `unknown` while it is new, resized, typed at, or back at its prompt after a command or a hosted agent exits, and is `working` only while a command in front of it prints (`cargo build`, `ls -R /`). A shell pane whose program doesn't do job control (`sh -c …` as its `argv`) is always in front, so its output never counts.
- **Hosted agents:** a shell pane runs the `shell` rules until its foreground process is `claude` or `codex`, as that agent's `process` list (its rule file's, so an override applies) names it. From then on the pane **hosts** that agent (`hosted_agent`, §3): it runs that agent's rules, and goes back to the `shell` rules once the agent leaves the foreground (it exits, or the user suspends it).
  - A listed name other than the agent's own, such as `node` for an npm install of Claude Code, counts only while the process runs the agent's script: its first argument that isn't a flag is a file named after the agent (`…/bin/claude`, `codex.js`), or sits in its npm package (`@anthropic-ai/claude-code`, `@openai/codex`). So `node server.js` in a shell is still a shell.
  - The foreground process is read on every state tick (100 ms), so a hosted agent registers within a tick of reaching the foreground. A tick that can't read it changes nothing.
  - On each change the state starts over: the pane publishes `unknown` (unless it already was), then whatever the new rules settle on, so the shell's `working` can never turn into the agent's `done`. Input queued for `idle` (§4) is dropped, so text meant for the agent is never typed into the shell, nor the other way round.
  - The daemon saves `hosted_agent` to the pane's row, then sends a `changed` pane event (§5).
  - Only `claude` and `codex` are hosted: a rule file for another agent (`rules/aider.toml`) applies to no shell pane.
- **Terminal modes after a program:** once a pane's process exits, and once the agent a shell pane hosts hands the terminal back to the shell, the daemon writes `agentdeck_core::ws::RESET_MODES` into the pane's `Term` and sends it to every attached client as output: mouse reporting (9, 1000, 1002, 1003, 1005, 1006, 1015, 1016), focus events (1004) and bracketed paste (2004) off, normal cursor keys and keypad, the main screen again (1049), the cursor shown in its default style; the screen and the scrollback stay. A killed full-screen program (Codex) leaves these on, and clients would otherwise keep sending mouse reports to the shell or to the agent started again (#322). A shell's hand-back is seen on its first output with its own process group in the foreground, before its prompt turns any of them back on, else on the next state tick. A respawned pane starts with a fresh `Term`.
- **v1 ships rules for `claude` and `codex`,** both from recorded sessions.
- **`claude`** (from Claude Code v2.1.325, recorded at 120×40 in the default inline TUI and in the fullscreen one with a status line; foreground process `claude`, or `node` for some npm installs):
  - The OSC 0 title is a state glyph and the session's name: `✳ Claude Code` at a fresh prompt, then a name Claude Code makes up after the first turn (`✳ Ok`). The glyph is `✳` when idle, a half-circle spinner (`◐`, `◑`) while it thinks, streams or runs a tool, and `✳` again on a permission prompt. The rules read `working` from a spinner (Braille as well, which versions before v2.1.228 drew) and `idle` from `✳`, below the dialog rule.
  - Dialogs are read from the screen by the key hint on the bottom non-blank row (`bottom:1`), which model output can't reach because the footer holds it otherwise: `Enter to confirm · Esc to cancel` under the folder trust dialog (`Accessing workspace:` … `Yes, I trust this folder`) and other select dialogs, and `Esc to cancel · Tab to amend` under a tool permission prompt (`Do you want to proceed?` … `1. Yes`). In the fullscreen TUI the dialog replaces the composer and its hint is still the last non-blank row.
  - The inline footer adds `esc to interrupt` while a turn runs; a rule reads it from the bottom row, for when the title is missing. The fullscreen footer with a status line doesn't show it.
  - No OSC 9;4. OSC 7501 only as a startup probe, `ESC ] 7501 ; ? BEL`, which agentdeck doesn't answer; no state follows it. The rules keep OSC 7501 and 9;4 entries should Claude Code start sending them unprompted.
  - These correct the spike's notes in two places: the title doesn't keep `Claude Code` once a session has a name, and it shows `✳`, not a spinner, on a permission prompt, so only the screen tells blocked from idle. The trust dialog now preselects `No, exit`.
  - After `/exit` it clears the title and prints `claude --resume <session id>`; no rule matches, and the process exit publishes `exited`.
- **`codex`** (from codex-cli 0.169.0, recorded at 120×40; foreground process `codex`):
  - OSC 7501 carries every state: `state=idle` at a fresh prompt, `working` while it thinks, streams or runs a command, `done` when a turn finishes, `blocked` (`kind=permission`) on an approval prompt, and `clear` on exit. The rules map `blocked`, `working`, and `idle`/`done`/`error` straight across.
  - Two dialogs are read from the screen, ahead of OSC 7501, by the key hint on the bottom non-blank row (`bottom:1`), which model output can't reach because the footer holds it otherwise:
    - the approval prompt (`Would you like to run the following command?` … `Press enter to confirm or esc to cancel`), should OSC 7501 not flag it;
    - the folder trust dialog (`Trust this folder?` … `enter continue · esc back`), which comes before any OSC 7501.
  - The OSC 0 title is the folder name, with a Braille spinner in front while working and `[ ! ] Action Required |` in front when blocked. Users can choose what the title shows, so no rule reads it. Codex sends no OSC 9;4.
  - After `/exit` it sends OSC 7501 `clear` and prints `codex resume <session id>`; no rule matches, and the process exit publishes `exited`.
- **Tests:** every rule set has unit tests that feed **recorded terminal output** (`tests/fixtures/<agent>/*.bytes` plus the expected state) through a `Term`.
- **Recording fixtures:** `script/record-pty.py --out DIR --steps FILE -- <argv>` runs the CLI in a 120×40 PTY with `TERM=xterm-256color`, answers the terminal queries a TUI waits on, types what a steps file says (`wait <regex>`, `sleep`, `send`, `mark <name>`, `end`), and writes the raw bytes since each `mark` to `<name>.bytes`, with each mark's foreground process and OSC sequences in `marks.log`. Each fixture continues the one before it, so a test feeds a chain in order. To re-record `codex`, run the `*.steps` files beside its fixtures, each of which names its flags:
  - Run it in a throwaway git repo (`mktemp -d /tmp/agentdeck-codex-XXXXXX`: no `.` in the path, since `-c` splits its key on dots), never a real one, with trivial prompts; it uses the account's quota.
  - Pass everything as flags; don't edit `~/.codex/config.toml`. `-a on-request -s read-only` plus a prompt asking for a command with escalated permissions forces an approval prompt (0.169.0 dropped `untrusted`). `-c 'projects.<dir>.trust_level="trusted"'` skips the trust dialog; the quoted TOML key form doesn't. Record the trust dialog with no flags and end it without answering, since answering saves the choice to `config.toml`.
  - Sleep a second before sending Enter, or Codex takes the text and the Enter as one paste.
  - Wait on text the prompt itself doesn't contain.
  - To re-record `claude`, run its `*.steps` files the same way, each naming its flags, with an allowlisted environment (`env -i PATH=… HOME=… USER=… SHELL=… LANG=…`). Never pass `CLAUDECODE` or `CLAUDE_CODE_*` through from a Claude Code session.
    - `--setting-sources project,local --strict-mcp-config` keeps the user's settings, hooks, plugins, status line and MCP servers out of the recording; `--model haiku` keeps it cheap; `--permission-mode manual` makes a Bash command that writes (`touch a.txt`) ask, since auto mode was on by default and read-only commands like `echo` never ask; `--session-id <uuid>` launches it as agentdeck does.
    - Claude Code has no flag to skip the trust dialog, and answering `Yes, I trust this folder` saves it to `~/.claude.json`. Trust is inherited from a trusted parent folder, but inside a git repo only up to the repo's root, so record the trust dialog in a fresh `mktemp -d` git repo and end it without answering, and record the sessions in a `mktemp -d -p <a folder trusted once>` that isn't a git repo.
    - Wait on single words (`proceed`, `confirm`), since Claude Code moves the cursor between words, and on the title (`\x1b\]0;✳`, `\x1b\]0;(?!✳)`) for a turn's start and end.
  - Scrub before committing: the temp dir's random suffix (also where the renderer split it with a cursor move), session ids (to `00000000-0000-7000-8000-000000000001` for `codex`, `00000000-0000-4000-8000-000000000001` for `claude`), the plan label in Claude Code's banner (to as many `X`s, e.g. `Claude XXX`, so cursor positions hold), and any home path, user, org, email or account name. Render the chain afterwards and check the screens' text too, since the renderer may split a word with cursor moves. Keep the bytes otherwise as recorded; trimming is only cutting a chain's last fixture at a frame end (`ESC [ ? 2026 l`).

## 8. PR sync

- **Token:** the daemon uses the first source that gives one: a **saved token** in the system keyring, then `GH_TOKEN`, else `GITHUB_TOKEN`, from its own environment (empty is the same as unset), then `gh auth token`. The saved token wins because an env var is easier to forget than an app setting. A token GitHub rejects doesn't send the daemon on to the next source.
  - **Re-read:** it reads the sources at start, again after a 401, and again whenever the auth routes (§4) save or delete the token; while there is none, every sync reads them again. While the token came from `gh`, every sync and close first runs `gh auth token` again, and reads the sources again when it fails or prints another token: `gh auth logout` doesn't revoke the token, so GitHub would go on taking it, and no 401 would come. Each read checks the token it finds with `viewer { login }`, keeping the login and the `X-OAuth-Scopes` header for `GET /v1/github/auth`, and sends `github_auth` (§5) when the source, login or `rejected` changed. A change through the auth routes also starts a sync at once. No token, or one GitHub still rejects after that re-read, means `GET /v1/prs/status` reports `logged_out` (with `last_error` "GitHub rejected the token" for a rejected one), and the GUI shows a banner (§11); `GET /v1/github/auth` then keeps the rejected token's `source`, with no `login` and `rejected: true`, and sends `github_auth`, also when GitHub accepted the token at the re-read and rejected it on the next request. A saved token stays saved: Sign in with GitHub or a pasted token replaces it, and Sign out deletes it. A check that fails for another reason (GitHub down) keeps the token, and the login GitHub last gave for it.
  - **Credentials** live only in the system keyring, through `keyring-core` and the keyring project's Secret Service store (`zbus-secret-service-keyring-store`), connecting on each call, so a keyring that starts or unlocks after the daemon is found. A call that takes over 10 s (a locked keyring waiting on a prompt) counts as no keyring. The daemon owns it, so PR sync runs while the GUI is closed. The token and the OAuth client ID are never in a file (`config.toml`, `daemon.json`, the database), a log, an error, an event or a response, and never added to a pane's environment: a pane gets only what §6's allowlist passes from agentdeckd's own environment, so a `GH_TOKEN` the user exported reaches it as it reaches their shell, while a saved token or the client ID never does. `last_error` and log lines carry GitHub's message, never a request's headers.
  - **Keyring entries** are under the service `agentdeck`. The token's is named `github.com/<login>`, so a later version can hold more than one account; v1 holds one, and saving a token deletes any other `github.com/` entry. The daemon finds it by searching the service's entries, so no file names the login. The OAuth client ID is a separate entry, `oauth-client-id@github.com` (no GitHub login holds an `@`).
  - **No keyring** (headless, or no Secret Service on the session bus): reading finds no saved token and goes on to the environment. Saving a token or a client ID, and starting a sign-in, is `503 no_keyring`: "No system keyring is running, so agentdeck can't save a token. Set GH_TOKEN in agentdeckd's environment instead."
  - **Pasting a token** (`PUT /v1/github/token`): the daemon checks it with `viewer { login }` before saving. A 401 is `422 invalid_token` ("GitHub didn't accept this token.") and saves nothing; any other failure is `502 github_error`. GitHub's `X-OAuth-Scopes` says what a classic token may do. One without `repo` or `public_repo` still saves, and clients warn "PR sync works; closing PRs needs repo". A fine-grained token sends no scopes header; it saves, and clients note "Closing works only on repos you own". Clients show both from `scopes`, for whichever source gives the token.
- A sync every 120 s (the first at start), and on `POST /v1/prs/sync`. One sync runs at a time.
  - **Asked for:** Sync now on the Pull requests view and `agentdeck pr sync` send `?full=true`, so the sync is full whatever sync is due: a PR stored in the wrong state that GitHub hasn't updated since, which no incremental search finds, is put right at once rather than at the hourly full sync. A request that comes while a sync runs gets a full sync right after it, as a widened cutoff does, and answers once that one finishes; one that fails leaves the next sync full. Without `full`, the request runs the sync that is due. An older daemon ignores `full`. `AGENTDECK_GITHUB_API` replaces the GraphQL URL (`https://api.github.com/graphql`) and `AGENTDECK_GITHUB_REST_API` the REST API's base URL (`https://api.github.com`); tests point both at httpmock. A request gives up after 30 s; `AGENTDECK_GITHUB_TIMEOUT_MS` replaces that (tests use it).
  - **Age cutoff:** only PRs GitHub updated in the last `max_age_days` days sync: the setting `pr_sync.max_age_days` (§2), default `90`, `0` for no cutoff. Each sync reads it as it begins, so a PATCH applies to the next sync, and widening it (more days, or `0` where there was a cutoff) starts a full sync at once, after any sync running, so the older open PRs it now lets in arrive without waiting for the hourly full sync. Narrowing it waits for the next sync. `AGENTDECK_PR_MAX_AGE_DAYS` overrides the file (tests use it); empty is the same as unset, and a value that isn't a count of days is logged and ignored. The cutoff is that many days before the sync began.
  - **Full:** the first sync, the first after an hour since the last full one (`AGENTDECK_PR_FULL_SYNC_SECS`, `0` for every sync), the next one after the age cutoff widens, one asked for with `full`, and the first with another token than the last good sync ran with or after a sync found none (a sign-in, a sign-out then a sign-in, a token pasted, `gh` logged in to another account), so every PR is checked again with what the new sign-in can see at once; in two phases. First the list `viewer.pullRequests(states: OPEN)`, 100 a page, most recently updated first, with light fields only (no review, no checks); each page is stored as it arrives, a stored PR keeping its review and checks. The list stops at the first PR updated before the cutoff: neither it nor anything after it is stored, and no later page is read. Then every field, fetched by number, for the PRs that are new, that GitHub updated since they were stored, or that are unsettled (below).
  - **Incremental:** the rest search `is:pr author:@me updated:>=<T>`, where `T` is 10 minutes before the last good sync began, so a merged or closed PR comes back in its new state. A merged or closed PR not stored as open is skipped, and so is any PR updated before the cutoff. Then the unsettled open PRs the search left out, updated within the cutoff, are fetched by number; Finished and unreachable PRs are left out. Nothing is found unreachable.
  - **Unsettled:** a PR whose checks are `pending` or none (none had started when it was stored), or whose review is `review_required` or `changes_requested`. A check run finishing doesn't update a PR, so the search misses it. A submitted review does update it, to the second (checked on public PRs, #247), so a change requested on an `approved` PR comes back in the search. No review decision means the repo requires none, and `approved` waits on nobody. Each incremental sync costs one more request per 25 unsettled PRs.
- `POST /v1/prs/sync` answers once its sync finishes, with the same body as `GET /v1/prs/status`: `{ login: "logged_in"|"logged_out", last_synced_at, last_error, progress, max_age_days, synced_as? }`. `max_age_days` is the age cutoff the next sync uses (`0` for none), so clients never read `config.toml` themselves. `synced_as` is the login GitHub gave for the token of the last good sync, stored in `pr_sync`, so it outlasts a sign-out and a restart: the logged-out banner says whose PRs show (§11). Signing out changes no stored PR. A failed sync is still 200, with `last_error` set: `GitHub answered <status>`, plus GitHub's `message` when the body is JSON. A request that fails with a 5xx or in transit is tried up to 3 times, 1 s then 2 s apart. One that fails in transit says why: "GitHub didn't answer in time", "couldn't connect to GitHub", "couldn't read GitHub's response" or "calling GitHub failed", then the URL without credentials, query or fragment, then the causes reqwest gives (`operation timed out`, `tcp connect error: Connection refused (os error 111)`, a DNS or TLS error), e.g. `GitHub didn't answer in time (https://api.github.com/graphql): operation timed out`. A close's `error` reads the same.
- **Repository:** every read of a PR, the list's light fields included, takes its repository's GitHub id (`fullDatabaseId`), `owner/name`, URL, private and archived, its base branch (`baseRefName`) and its author's login (`author`, null once the account is gone). Each Repository is stored by its id (§3): one PR sync hasn't seen is created, and a new `owner/name`, URL, private or archived for a known id updates it, so a rename or a transfer keeps the Repository and its PRs. A stored PR is found by its Repository's id and number (§3), so GitHub showing it under a new name updates its row rather than making a new one, and another Repository that took the old name has PRs of its own, however the two are listed. Each Repository created or changed sends `changed` `repository` (§5) once per store. The full sync's PRs that "left the list" are worked out by Repository id and number after the list is stored, so a renamed Repository's PR, listed under its new name, hasn't left it; the incremental sync keeps a merged or closed PR it finds when its Repository's id and number are stored open. A fetch by number asks by the name the Repository last went by; one GitHub answers with another Repository's PR (the name was taken by another before PR sync saw the rename) counts as not shown. A PR GitHub gives no Repository id for (`fullDatabaseId` null) can't be stored and is left out.
- Each result is kept as a **Pull request**, with its title and every field above; nothing else is made of it. agentdeck no longer files PRs under Workspaces itself: a Workspace's Pull requests are those of the Repositories it links (§3, §4).
  - **New, merged, closed, reopened:** the PR is stored as GitHub shows it. In a full sync, PRs that left the list are fetched by number, once. Fetches by number go 25 to a request, 4 requests at a time.
  - **Unreachable:** a PR fetched by number that GitHub doesn't show to the token (no repository or no pull request: not found, or no access, as for a fine-grained token that reaches other repos, or a PR synced under another account) is not stored as closed. It is marked unreachable (`unreachable_at` set, a `changed` event), keeping its state and every field as last synced. It stays stored `open`, so each full sync fetches it again; the incremental sync's unsettled fetches leave it out, and it can't be closed (below). Clients show it dimmed and leave it out of PR counts (§11). Once GitHub shows it again (in the list, a search or a fetch), it is no longer unreachable, and is stored as GitHub shows it. Unreachable PRs get no Finished window: one last updated before the cutoff is not Finished, and none is deleted; it stays, marked, until GitHub shows it again.
  - **Finished:** a kept PR becomes Finished (`finished_at` set to when the sync stored it so) once the sync stores it merged or closed, and a PR closed from agentdeck (below) is Finished at once. In a full sync, a reachable PR stored as open that left the list and was last updated before the cutoff is not fetched: it is Finished instead, still `open`, once (a `changed` event). Nothing changes on GitHub. A Finished PR stays Finished from the first time it was, until GitHub shows it open within the cutoff (in the list or a search): then it is no longer Finished.
  - **Leaving:** at the end of each good sync, every PR Finished 7 days ago or more (`AGENTDECK_PR_FINISHED_SECS` replaces the 7 days, `0` for none; tests use it) is deleted (a `changed` `pull_request` event each), unless it is unreachable, and then each of their Repositories that no Link and no kept PR references any more (a `changed` `repository` event each). `GET /v1/prs` leaves Finished PRs out unless asked (§4); clients leave them out of PR counts and show them only under Show finished (§11).
- `checks` and `review` come from `statusCheckRollup` (`ERROR` counts as failure, `EXPECTED` as pending) and `reviewDecision`. Every PR in the API carries `unreachable`, true while the GitHub sign-in can't see it (above).
- A sync stores each page as it arrives, and each PR it stores for the first time or changes gets a `changed` `pull_request` event (§5) then. While it runs, the status's `progress` is `{ prs_done, prs, stage }` (`prs` from the search's count, `0` until the first page answers; `stage` is `listing`, then `details` while reviews and checks are fetched by number), and every change to it sends a `pr_sync` event. Clients show it: "Syncing… 100 of 271 PRs", then "Syncing details…".
- **Sign in with GitHub** is the OAuth device flow, asking for the scope `repo` once.
  - **Client ID:** the user registers an OAuth App on GitHub, with Enable Device Flow on and no client secret. Its client ID is never committed: the user enters it in Settings, and it is saved in the keyring (`PUT /v1/github/client-id`) like the token. `AGENTDECK_GITHUB_CLIENT_ID` gives it while none is saved; a saved one wins, as the token does. With neither, `POST /v1/github/device` is `409 no_client_id`, and clients hide Sign in. `PUT` refuses a blank one, and one shaped like a user code (`^[A-Z0-9]{4}-[A-Z0-9]{4}$`, as `WDJB-MJHT`: the sign-in's code, pasted in by mistake), with `400 invalid_client_id`: "The OAuth client ID is blank." or "That looks like the sign-in code, not a client ID.", and saves nothing. No error or log line names the client ID.
  - **Start:** `POST /v1/github/device` checks that the keyring can save, then asks GitHub for a device code (`POST https://github.com/login/device/code` with the `client_id` and `scope=repo`) and answers `{ user_code, verification_uri, expires_at }`. A refusal (Device Flow off) is `502 github_error` with GitHub's `error_description`, else its `error`. A client ID GitHub doesn't know gets a 404 `{"error":"Not Found"}` with no description, which tells the user nothing, so a 404 or a bare `Not Found` is `502 github_error` with "GitHub doesn't know this OAuth client ID. Check it in Settings → GitHub." `AGENTDECK_GITHUB_OAUTH` replaces `https://github.com`; tests point it at httpmock.
  - **Polling:** the daemon then polls `POST https://github.com/login/oauth/access_token` (`grant_type=urn:ietf:params:oauth:grant-type:device_code`) at GitHub's `interval`, 5 s slower after each `slow_down`. On a token it saves it as a pasted one is (without the scope notes, since it has `repo`), re-reads, and sends `github_auth` with `device: "signed_in"`. `expired_token`, or `expires_at` passing, sends `device: "expired"`; `access_denied`, `device: "denied"`; any other error, `device: "failed"` with GitHub's message. Each of those ends the polling. A poll that fails in transit is tried again at the next interval, until `expires_at`. An `interval` under 1 s counts as 1 s.
  - **Log:** the start, with the code's expiry and the interval, at info; each poll that fails in transit at warn, with why; each `authorization_pending` at debug, with the count so far; and how the sign-in ended, or that it was cancelled (by `DELETE`, or a new `POST`), at info, with the count of polls, pending answers and transit failures. No line carries the client ID, the device code, the user code or the token.
  - **Cancel:** one sign-in runs at a time, so a new `POST` cancels the one before. `DELETE /v1/github/device` cancels it (204, also with none running) and sends no event.
- **Looking up a Repository** (`GET /v1/repositories/resolve`, and linking one agentdeck doesn't know, §4) is agentdeck's REST call to GitHub: `GET /repos/{owner}/{repo}` with the token as a bearer, `Accept: application/vnd.github+json` and `X-GitHub-Api-Version: 2022-11-28`, reading `id`, `full_name`, `html_url`, `private` and `archived`. GitHub redirects an old name to the renamed Repository, so the answer carries its name now. It uses the token as PR sync does (a `gh` token is checked first, a 401 reads the sources again and tries once more, then counts as rejected), the same 30 s timeout, the same retries (after 1 s and 2 s, on a 5xx or a request that failed in transit) and the same wording for a failure. A 404 is a Repository GitHub doesn't show the sign-in (no such repository, or no access): `400 unknown_repository`, "GitHub can't see owner/name. Check the name or your token's access." No token, or one GitHub still rejects, is `409 not_signed_in` ("Sign in to GitHub to look up owner/name.", or "GitHub rejected the token, so agentdeck can't look up owner/name."); any other failure is `502 github_error`.
- **Closing PRs** (`POST /v1/prs/close`) closes them only: no comment, no branch delete.
  - Each PR is named by its reference, `owner/name#123` (or its GitHub URL, which clients turn into one), and found by its Repository's name and its number, ignoring case as GitHub does; the name follows the Repository's renames, so the name GitHub gives it now finds it. It must be stored `open`, Finished ones included, and not unreachable; any other, and one agentdeck doesn't keep, fails with "Not an open PR" and never reaches GitHub. With no token, every one fails with "Not signed in to GitHub". The results come back one per reference, in the order asked, each naming the reference asked for.
  - The daemon reads the PRs' node ids by Repository name and number, 25 to a request as fetches by number go. Then it closes each PR on its own, one at a time, with its own GraphQL `closePullRequest` mutation, since GitHub has no batch close.
  - A close is sent again only when its connection failed (refused, host not found), so it never reached GitHub. After a timeout or a 5xx it may have taken effect, so the daemon reads the PR's state once instead, without retries: `CLOSED` counts as closed; any other state fails with the close's error; a failed read fails with "GitHub didn't answer; check the PR".
  - A PR GitHub closes is stored as `closed` and Finished at once (a `changed` `pull_request` event), with no fetch by number on the next sync.
  - A failure is that PR's alone: its result is `ok: false` with `error`, GitHub's message (a token without write access fails this way, per PR) or why the request failed, and the rest still close. It answers once every PR is tried.

## 9. Handing work to agents

agentdeck doesn't brief agents. There are no tasks, no comments, no workspace Instructions, no launch prompt (§6) and no brief: an agent reads its own CLAUDE.md or AGENTS.md, and you hand it work by pasting into its pane or with `agentdeck agent send <pane> <text>` (§10), which waits until the pane is `idle` (§4).

- **Nothing types on its own:** the daemon types into a pane only what a client sends with `input` (§4).
- A pane links to nothing: no task, no PR. Tasks come back later as a board, a separate effort.

## 10. CLI

`agentdeck` (clap) reads `daemon.json` and starts the daemon when it isn't running: no file, a pid that isn't running, or a live pid that doesn't answer `/v1/health` within 1 s while nobody holds the lock (§2). A live daemon that holds the lock and can't be reached is an error, never a second daemon (§2). It starts `$AGENTDECK_DAEMON` if set, else the `agentdeckd` beside its own executable, else `agentdeckd` from `PATH`, in its own process group with no terminal, and waits up to 20 s for a `daemon.json` that answers `/v1/health` (the daemon may first wait for one that is shutting down, §2). Output is human-readable, or with `--json` the API's own objects (`ws rm` prints `{id, deleted}`, `tail` prints `{pane, output}`). A failure prints `agentdeck: <message> (<error_code>)` to stderr and exits 1; `agent new`'s `invalid_argv` prints the message alone (§6).

```
agentdeck ws ls | new <name> | rename <ws> <new-name> | archive <ws> | mute <ws> | unmute <ws> | rm <ws>
agentdeck agent ls [--ws WS] | new --ws WS [--agent claude|codex] [--cwd DIR] | send <pane> <text> [--now] | stop <pane>
agentdeck repo ls [--ws WS] | link <repo> --ws WS | unlink <repo> --ws WS
agentdeck pr ls [--repo R] [--ws WS] | sync | status | close <pr>… [--yes]
agentdeck config ls | get <key> | set <key> <value>
agentdeck daemon restart
agentdeck tail <pane> [--bytes N]
```

- A `WS` or `<ws>` is a workspace's id, slug or name, tried in that order; a name two workspaces share is an error that lists their slugs.
- A `<pr>` is a pull request's reference, `owner/name#123`, or its GitHub URL (`https://github.com/owner/name/pull/123`, also with a tab such as `/files` after it); an `R` or a `<repo>` is a Repository's `owner/name` or its GitHub URL. No short ids. The CLI reads them before calling the daemon (`agentdeck_core::{PrRef, RepositoryName}`), so text that names neither is clap's usage error, which says what to write instead: "`acme/widgets` isn't a pull request: write owner/name#123 or its GitHub URL", "`widgets` isn't a Repository: write owner/name or its GitHub URL".
- A `<pane>` is the whole id or a short id: 6 or more of its hex digits in a row, dashes ignored, such as its last 8. A UUIDv7's leading digits are its creation time, shared by ids made close together, so its random tail is what tells them apart. The CLI resolves a short id itself, against the layouts of every workspace's tabs (as `agent ls` reads them). Fewer than 6 hex digits is an error (`invalid_id`), as are digits no id holds (`not_found`) and digits several ids hold (`ambiguous_id`), which lists each match with its workspace's slug and tab's title.
- A workspace has no folder (§3), so no `ws` command takes, makes or removes one.
- `ws ls` lists every workspace, archived ones included, oldest first, with `GET /v1/workspaces` and the Repositories each links (`GET /v1/repositories`): a line per workspace under `ID  SLUG  NAME  REPOSITORIES`, an archived one's name marked `(archived)`, then the names (`owner/name`) of the Repositories it links, in `repo ls`'s order, separated by `, `, or `-` when it links none; "no workspaces" when there are none. With `--json` it prints each Workspace object with `repositories` added: the list of those names, empty when it links none.
- `ws new <name>` creates a workspace with `POST /v1/workspaces` and prints `<id>  <slug>`, or the Workspace with `--json`. It takes no `--dir` and no `--repo`: link Repositories afterwards with `repo link`.
- `ws rename` sets a workspace's name with `PATCH /v1/workspaces/{id}` and prints the workspace as `ws ls` does, under its header (`--json`: the workspace). Its slug stays, so the old slug still finds it; a blank name is the daemon's `invalid_name`.
- `ws rm` deletes a workspace with `DELETE /v1/workspaces/{id}` (§4): its panes stop and its Repositories are unlinked, and no folder is touched. It has no `--force`. It prints `deleted <ws>`, or `{id, deleted}` with `--json`.
- `agent ls` lists every pane, agent and shell, in the layouts of the tabs of `--ws`'s workspace, else of every workspace, in workspace, tab and layout order, read with `GET /v1/workspaces`, `GET /v1/workspaces/{id}/tabs` and `GET /v1/panes/{id}`. A pane whose process exited is listed, `exited`, until it is closed. It prints a line per pane under `ID  WORKSPACE  TAB  AGENT  STATE  FOLDER`: the workspace's slug, the tab's title, the agent (`claude`, `codex`; for a shell pane `hosting <agent>` while it hosts one, else `shell`), the state (§7) and the pane's current folder (§6) as an absolute path; "no panes" when there are none. With `--json` it prints a list of the panes' own objects, `folder` included, each with `workspace_id`, `workspace` (the slug) and `tab` (the tab's title) added. The ids it prints are what `agent send`, `agent stop` and `tail` take, whole or short.
- `agent new` launches the agent with `POST /v1/panes` (no `argv`: the daemon builds it, with no prompt, §6) in `--cwd`, made absolute, or the CLI's own current folder, so run inside a pane it starts where that pane is. The pane goes in the workspace's first tab with no panes, else in a new tab titled after the agent, and becomes that tab's layout. A tab made for a launch that fails is deleted.
- `agent send` submits the text with `input` `submit: true` (the text, then Enter in a write of its own, §4), with `when: "idle"`, so a busy agent gets it once its pane is idle, or `"now"` with `--now`. It prints `queued until <pane> is idle` or `sent to <pane>`, and `{queued}` with `--json`. It is how you hand an agent work from a script (§9).
- `agent stop` stops a pane's agent with `POST /v1/panes/{id}/stop` (§4) and keeps the pane: an agent pane's process, which `agent ls` then lists `exited` and the GUI's **Restart agent** resumes, or the agent a shell pane hosts, leaving the shell running. It prints `stopped <pane>`, and `{id, stopped}` with `--json`; a pane whose process has exited is the daemon's `exited`, a shell hosting no agent its `no_agent`.
- `config` names a setting by its dotted key (§2). `ls` prints each key and value, and `set` the key it set, adding "(an environment variable overrides config.toml)" to an overridden one; with `--json`, both print the settings object. `get` prints the value alone, or `{key, value}` with `--json`; a key that isn't a setting is an error. `set` sends a value that reads as a number, `true` or `false` as that, anything else as text, and the daemon checks it (`invalid_setting`).
- Every command except `daemon restart` prints one line to stderr, after `agentdeck: `, when the daemon is older than the CLI (§2), then runs as usual: "warning: agentdeck's background service (agentdeckd) is older than this CLI. Run agentdeck daemon restart to use new features; your agents resume after the restart."
- `pr sync` runs a full sync (`?full=true`, §8), as Sync now does. `pr sync` and `pr status` print the status (§8) a line each: `github:` `logged_in` or `logged_out` (whichever source gives the token), `last sync:` its time or `never`, `syncing:` its progress while one runs, and `last error:` while the last one failed.
- `repo ls` lists the Repositories agentdeck keeps with `GET /v1/repositories` (§4), with `--ws` only those that workspace links: a line per Repository under `REPOSITORY  WORKSPACES`, its name marked `(unreachable)` while the GitHub sign-in can't see it, then the slugs of the workspaces that link it, oldest first, separated by `, `, an archived one marked `(archived)`, or `-` when none does; "no repositories" when there are none. With `--json` it prints the list of `RepositoryLinks` objects, each with its workspaces' ids.
- `repo link` links a Repository to a workspace with `POST /v1/workspaces/{id}/links` (§4): one agentdeck doesn't know is looked up on GitHub first, and one GitHub doesn't show the sign-in is the daemon's `unknown_repository`, "GitHub can't see owner/name. Check the name or your token's access.". It prints `linked <owner/name> to <ws>`, the Repository by its name now, or the `RepositoryLinks` with `--json`.
- `repo unlink` finds the Repository among those the workspace links (`GET /v1/repositories?workspace=`), by name ignoring case, and unlinks it with `DELETE /v1/workspaces/{id}/links/{repository}`; one the workspace doesn't link is an error, "owner/name isn't linked to <ws> (not_found)". agentdeck forgets the Repository when no other workspace links it and none of your PRs belongs to it (§3). It prints `unlinked <owner/name> from <ws>`, or `{workspace_id, repository_id, unlinked}` with `--json`.
- `repo link` and `repo unlink` need `--ws`, and no `repo` or `pr` command defaults a workspace from `$AGENTDECK_WORKSPACE`, so a command prints the same wherever it runs: an agent passes `--ws "$AGENTDECK_WORKSPACE"` itself.
- `pr ls` lists the pull requests agentdeck keeps that aren't Finished (§8) with `GET /v1/prs` (§4), with `--repo` only that Repository's and with `--ws` only those of the Repositories that workspace links: a line per PR under `PR  STATE  TITLE`, the PR by its reference and its state `open`, `draft` (an open draft), `merged` or `closed`, then `, unreachable` while the GitHub sign-in can't see it (§8); "no pull requests" when there are none. With `--json` it prints the list of `PullRequest` objects.
- `pr close` closes the pull requests it names with `POST /v1/prs/close` (§8). Without `--yes` it first prints "Close N PRs on GitHub? Their repos' owners will see them closed. You can reopen a PR on GitHub." then a line per repo with its count ("  acme/widgets  2 PRs"), and asks `[y/N]` on stderr; anything but `y` closes nothing, prints "Closed nothing" and exits 0. Without `--yes` and with no terminal on stdin, it is an error that names `--yes`. It prints `closed <pr>` or `failed <pr>: <error>` per PR, by its reference (`closed acme/widgets#7`), then "Closed 12 of 14" when any failed, and exits 1 then; `--json` prints the results object.
- `daemon restart` restarts the daemon as §2 says (starting one when none runs) and prints `restarted agentdeckd, now pid <pid>`, or `{pid, version, api_version}` with `--json`.
- **Inside a Pane** `agentdeck` is on `PATH` (§6), and `$XDG_RUNTIME_DIR` from the Pane's environment leads it to the same daemon, so an agent runs it like any other command. `AGENTDECK_PANE` and `AGENTDECK_WORKSPACE` are set in every pane's environment, added on top of the allowlist (§6). No command defaults from them.

The sidebar's open-PR count keeps `GitPullRequest`.
  - **Unreachable PR** (Penpot "Screens · Main" → "Pull requests · unreachable PR"): a Pull requests view row whose PR the GitHub sign-in can't see (§8) is drawn at opacity 0.5, the whole row (icon, title, cells and `…` menu) and still works. Hovering its title shows a tooltip above it: "Your GitHub sign-in can't see this PR. It's shown as it was last synced." It has no Close PR and no checkbox in Select mode, and it isn't counted in the sidebar's Pull requests count.
  - The terminal palette follows the theme. Terminal text is JetBrains Mono (`font-family.mono`).
- **Notifications:** the GUI shows OS notifications through the freedesktop notifications D-Bus API, named "agentdeck", with no icon, one hint, `desktop-entry` = `agentdeck`, and the server's own timeout; only while it runs, and the daemon sends none. Nothing about them is configurable in v1: no global mute, quiet hours or sounds.
  - **Desktop entry:** the hint names `agentdeck.desktop`, the file the repo ships as `packaging/agentdeck.desktop` (`Exec=agentdeck-gui`, `StartupWMClass=agentdeck`, the window's app id). Installed (`install -Dm644 packaging/agentdeck.desktop ~/.local/share/applications/agentdeck.desktop`), it lets the desktop tie the notifications to the app's window and its dock entry; without it they still show, under "agentdeck".
  - **One per tag:** each notification has a tag (`pane:<id>`, `pr:<Repository id>#<number>`, by GitHub's Repository id so a rename keeps it, or `prs`). A newer one for a tag whose notification is still open replaces it in place (`replaces_id`), so a pane or PR has at most one.
  - **Withdrawn:** a notification still open is closed (`CloseNotification`) once the user can see what it is about: the window is focused while the pane's tab shows on its workspace's Panes side, or, for a PR alert or "N PRs changed", while the Pull requests view shows. Clicking one closes it too, and quitting the GUI closes every one still open, so none outlives the app that could act on it.
  - **One connection:** `agentdeck-notify` holds one session-bus connection for the whole app and one task on GPUI's foreground that sends each `Notify` and reads the server's `ActionInvoked` and `NotificationClosed`, by the id the server gave each notification. A notification left open costs an entry in that id map, never a thread or a connection; it leaves the map once clicked, withdrawn or closed. (GPUI's own `show_system_notification` starts a thread and a connection per notification and holds both until the server closes it, #133.) Without a session bus the GUI logs why once and shows none.
  - **Panes:** an agent pane (not a shell, unless it hosts an agent) turning `blocked` or `done` while the user can't see it: its tab isn't the one shown, its workspace isn't or shows its Pull requests, or the window isn't focused. Title "<Agent> is blocked" / "<Agent> is done"; body "<tab title> · <workspace>". Once per state change, not again while the state holds.
    - **Reattach:** attaching resizes a pane to its view, and an agent redraws on a resize, so a done Claude Code can read working, then done again. For 10 s after a pane attaches (`attached`, §5), it turning back to the state it held then (`blocked` or `done`) notifies nothing: the user heard about that state already, from this GUI or the one before a restart. Another state notifies as usual, and so does the same state after the 10 s.
  - **PRs:** only Pull requests you authored alert: the PR's `author` is the login PR sync runs as (`synced_as`, §8), matched ignoring case; none alerts before a sync has run as a login. Review requests and assignments never alert, since GitHub already notifies them. The triggers: its checks turning `failure`, or its review turning `approved` or `changes_requested`. Title "Checks failed" / "Changes requested" / "Approved"; body "<owner/name> #<n> · <title>". **One alert per PR**, tagged by the PR: when several triggers fire at once the first of that order is the title, and a change in a later read replaces the PR's alert. Changes are held while a PR sync runs and shown when it ends, one per PR, the latest; more than 3 PRs changed in one sync make one "N PRs changed" whose body lists their "<owner/name> #<n>". None notifies while the user can see what it is about (Withdrawn, above): the Pull requests view.
  - Only changes between two reads count: what the GUI first reads after connecting (a pane already blocked, a check already failing) notifies nothing. A read after `resync` (§5) compares with what the GUI had, so it notifies as any other read does.
  - **Log:** each notification shown is logged at info with its tag (`pane:<id>`, `pr:<Repository id>#<number>`, `prs`) and title; one left out because what it is about is in view, one left out after a reattach, and one withdrawn, at debug.
  - **Muted:** a Muted workspace's panes never notify. A PR alert is muted only when every unarchived Workspace linking its Repository is Muted (`GET /v1/repositories`, §4, read with the sidebar's other reads): Archived Workspaces drop out of the rule, so a Repository linked nowhere, or only by Archived Workspaces, is Not in a workspace and its PRs always alert. Only Workspaces are Muted, never a Repository or a single PR.
  - **Click:** clicking a notification's body focuses the window and shows what it is about: the pane, in its workspace and tab; the Pull requests view at the PR's row for a PR alert (Landing on a row, above); the Pull requests view for "N PRs changed". Notifications offer no buttons.
- **Keymap:** `keymap.rs`, normal app shortcuts, `secondary-` bindings loaded with `KeyBinding::load`.
  - A binding wins over the terminal, so every shortcut is one a shell has no use for, after GNOME Terminal. Plain ctrl-letter, alt-letter, the arrows and the paging keys always reach the pane.
  - Tab and Shift+Tab go to the terminal when it has focus (completion in a shell, claude's mode switch); everywhere else they move focus.
  - Quit `secondary-shift-q`, asking first while agents run (Quitting while agents run, above); next / previous tab `ctrl-pagedown` / `ctrl-pageup` (or `ctrl-tab` / `ctrl-shift-tab`); tab 1–9 `alt-1`…`alt-9`; next / previous pane `secondary-shift-down` / `secondary-shift-up`, in layout order; new shell tab `secondary-shift-t`; split the focused pane with a shell right / down `secondary-shift-e` / `secondary-shift-o` (after Terminator); close it `secondary-shift-w`, asking first while it runs. Closing a tab's last pane closes the tab. A workspace's Panes / Pull requests switch `secondary-shift-p`; the tab and pane shortcuts apply on its Panes side only.
- **Logging:** `tracing`, to `$XDG_STATE_HOME/agentdeck/agentdeck-gui.log` (appended to, beside the daemon's `agentdeckd.log`, §2) and stderr, installed before anything else runs, with GPUI's `log` records bridged in. `RUST_LOG` picks the levels (`RUST_LOG=debug` shows the refused links above); without it, or when it doesn't parse, `info` and above. Without a state dir, or when the file can't be opened, the GUI logs to stderr alone and says why there; logging never stops it from starting.
